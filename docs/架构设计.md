# 黑灰产情报分析Agent系统架构设计文档

**版本**：V1.0  
**对应需求文档版本**：V1.0  
**设计目标**：定义系统的高层结构、组件划分、数据流转、通信机制和关键技术选型，确保系统满足功能和非功能需求，尤其在效果、成本、时延三角约束下实现最优平衡。

---

## 1. 架构设计原则

| 原则 | 说明 |
|------|------|
| **管道-过滤器模式** | 数据流经采集→清洗→分类→抽取四道工序，每道工序独立、可替换、可并行水平扩展 |
| **双通道差异化处理** | 90%+的数据走规则化零Token轻量通道，<10%的高价值数据走LLM+图谱的图谱构建通道，实现成本控制与深度分析统一 |
| **异步解耦** | 采集与处理通过消息队列解耦，LightRAG图谱构建可异步离线执行，不影响实时响应链路 |
| **Agent化编排** | 每个核心处理环节封装为独立Agent，由主控Agent调度，支持自然语言任务解析和流程组合 |
| **本地优先** | Embedding分类、文本处理等高频操作全部本地化，仅关键语义理解、图谱构建调用远端LLM，最小化外部依赖和延迟 |
| **可解释性内建** | 分类和实体抽取结果携带证据和来源，图谱关系可追溯，满足情报分析的可信度要求 |

---

## 2. 总体架构概览

系统采用**分层解耦**架构，从下至上划分为基础设施层、数据处理层、业务逻辑层和交互层，层与层之间通过明确的接口通信。

**各层职责**：

- **交互层**：提供用户输入查询的界面，将自然语言请求转发至主控Agent，并将最终结果格式化呈现。
- **业务逻辑层**：主控Agent作为大脑，负责解析意图、生成任务计划、调度流水线中的各个模块，并在处理过程中做出关键分流决策。查询/报告模块则专门负责从实体库中检索并组装最终答案。
- **数据处理层**：包含采集、清洗、意图分类、实体抽取等独立的处理模块，每个模块完成一个单一环节。它们由主控Agent调用，也可以被编排为自动运行的流水线（如定时采集、全量回溯）。
- **基础设施层**：提供数据持久化、消息传递、规则执行、模型推理等基础能力，是上层处理逻辑的支撑。

## 3. 核心组件详细设计

### 3.1 消息队列

**选型**：Apache Kafka（生产级推荐）或内存队列（原型验证）。

**作用**：
- 解耦采集与处理：采集模块高速写入原始消息，下游处理模块按自身节奏消费，避免数据源反压。
- 支持多消费者：清洗模块、归档服务等可独立订阅同一数据流。
- 削峰填谷：面对情报爆发期，消息堆积在队列中不丢失。

**消息主题设计**：
- `raw.messages`：原始消息主题，每条消息即为一个`RawMessage`对象。
- `cleaned.messages`（可选）：清洗后消息主题，用于后续分类模块消费。
- `deep.analysis.tasks`：图谱构建通道任务主题，存放高价值消息ID，供图谱构建通道处理。
- `image.analysis.tasks`：图片分析任务主题，存放需要VLM分析的图片信息，供图片处理模块消费。

### 3.2 图片处理模块

**角色**：对包含图片的消息进行低成本处理，提取结构化信息，并决定是否进入VLM分析。

**处理流水线**（两阶段过滤）：

#### 第一阶段：OCR优先处理
1. **图片下载与存储**：从RawMessage中提取图片URL/路径，下载并计算MD5哈希，存储到本地或对象存储。

   **图片下载容错**：下载失败时自动重试3次（间隔1秒、2秒、4秒），仍失败则记录image_url、error_msg、timestamp到错误日志，跳过该图片不阻塞主流程。

2. **OCR文字提取**：调用本地OCR（Tesseract/PaddleOCR）提取图片中的文字内容。
3. **正则结构化提取**：对OCR输出立即执行正则匹配，提取手机号、微信号、QQ号、URL、邮箱等高价值实体。
4. **黑库快速匹配**：将图片MD5与黑产图片样本库比对。命中则复用已知结论，**跳过VLM分析**。

#### 第二阶段：VLM分析（按需）
仅对以下条件同时满足的图片触发：
- OCR未提取到高价值实体
- 图片MD5未命中黑库
- 消息整体评分达到图谱构建通道阈值

5. **VLM语义描述生成**：调用本地轻量VLM（Qwen2-VL-2B）或云端VLM，生成图片语义描述。
6. **VLM结构化提取**：要求VLM以JSON格式输出实体列表。
7. **多模态文本融合**：将VLM描述拼接到消息文本，格式如`[图片语义] xxx`。
8. **新黑产图片上报与审核**：若VLM发现新型黑产套路截图，上报至审核队列。审核Agent（独立于VLM处理流程，作为第三者确保公平性）消费队列并执行二次确认。审核通过后写入黑库，下次同类图片可跳过VLM直接处理；审核不通过则记录日志后丢弃。

**Token消耗控制策略**：
- 优先使用本地轻量VLM，仅在本地模型不可用时调用云端API
- 设置单图Token上限（max_tokens=500）
- VLM调用量控制在图片总量的5%以内

**API接口降级策略**：
- 主API：DeepSeek
- 备用API1：Qwen（如主API失败/超时3秒）
- 备用API2：OpenAI兼容接口（如备用API1也失败）
- 所有API均失败时，记录错误日志，标记该消息为FAILED

**输出**：`ImageProcessingResult`对象，包含：image_md5、ocr_text、entities（regex提取的实体）、vlm_description（仅VLM分析后）、source（regex/ocr/vlm）、priority（high/low）

### 3.3 采集模块

**角色**：情报源适配器，负责从多源渠道抓取消息，并转换为统一格式写入消息队列。

**内部结构**：
- **渠道适配器管理器**：维护一个适配器列表，每个适配器实现统一接口：`start(keywords, time_range)`、`stop()`、`get_status()`。
- **TG适配器**：基于Telegram官方客户端库实现，支持文本消息、图片描述等。
- **通用Web适配器**：基于Scrapy或Requests实现，带IP代理池和频率控制。
- **格式化器**：将渠道特定数据转换为统一的`RawMessage` Schema。

**关键行为**：
1. **接收主控Agent下发的采集任务**（渠道、关键词、时间窗）。
2. 启用对应适配器执行定向采集。
3. 对抓取到的每条消息，即时格式化并发送至`raw.messages`主题。
4. 上报采集进度和状态。

### 3.4 清洗模块

**角色**：从`raw.messages`消费原始消息，执行标准化、去重、过滤，产出洁净消息流。

**处理流水线**（管道模式）：
1. **格式标准化器**：HTML标签剥离、Unicode规范化、全半角转换、emoji转文字描述。
2. **精确去重器**：计算文本MD5，与内存中的布隆过滤器+LRU缓存比较，24小时窗口。
3. **近似去重器**：SimHash计算与滑动窗口内的历史指纹比较，汉明距离≤3判定重复。
4. **噪声过滤器**：规则引擎（正则）剔除纯表情、纯符号、常见系统通知等。
5. **语言检测器**：调用本地fastText模型，标注语种并过滤非目标语言。

**输出**：`CleanedMessage`对象，写入`cleaned.messages`主题，或直接内存传递给分类模块（取决于部署模式）。

### 3.5 意图分类模块

**角色**：判断消息的风险类型，提供多级标签和置信度。

#### V2 三级漏斗 + 拒识 + 归一化（2026-06-05, commits `98bd93a` + `329471d`）

```
输入文本
    ↓
┌─────────────────────────────────────────────┐
│ Stage 1: 规则匹配 (regex / 关键词)          │
│   • 命中且 confidence >= 0.7 → 直接返回    │
│   • confidence 默认 0.9-0.95 (硬编码)        │
│   • 零 Token                                │
└─────────────────────────────────────────────┘
    ↓ (未命中)
┌─────────────────────────────────────────────┐
│ Stage 2: Embedding (Ollama bge-m3 + sklearn)│
│   • 1024D 向量 + LogisticRegression          │
│   • 拒识条件 (FR-CLF-07):                    │
│       max_proba < 0.45                       │
│       OR  margin (top1-top2) < 0.12          │
│   • 拒识 → source='embedding_uncertain'     │
│            → 强制 fallback 到 LLM           │
│   • 通过 → source='embedding' 直接返回     │
└─────────────────────────────────────────────┘
    ↓ (拒识或未达 0.6)
┌─────────────────────────────────────────────┐
│ Stage 3: LLM 兜底                            │
│   • LLMClient 多 provider 链 (MiniMax → Qwen)│
│   • 输出 JSON {level1, level2, confidence}   │
└─────────────────────────────────────────────┘
    ↓
[归一化 FR-CLF-06] 所有出口过 _normalize_level1_label
    ↓
clues.risk_label_level1 ∈ {5 个标准值}
```

**关键组件**：

| 组件 | 职责 | 代码位置 |
|---|---|---|
| `_classify_by_rules` | 静态关键词 + `pattern in text.lower()` 匹配 | `pipeline/classifier.py:258` |
| `_classify_by_embedding` (单条) | Ollama bge-m3 + sklearn 推理 | `pipeline/classifier.py:271` |
| `_classify_by_embedding_batch` (批) | 单次 batch Ollama 调用 + 向量化 predict | `pipeline/classifier.py:333` |
| `_classify_by_llm` | LLMClient 调用 + 强约束 Prompt | `pipeline/classifier.py:455` |
| `_normalize_level1_label` | 16+ 变体标签 → 5 个标准值 | `pipeline/classifier.py:172` |
| `_map_label_to_taxonomy` | embedding model 标签 → taxonomy level1/level2 (5+12 完整映射) | `pipeline/classifier.py:441` |
| `classify_batch` (主入口) | 三级漏斗编排，拒识时强制 fallback | `pipeline/classifier.py:599` |

**Stage 2 拒识的必要性**：当遇到明显无关内容（如"今天天气真好"）时，模型仍会从 5 个类别中硬挑一个概率最高的，confidence 0.5-0.7 之间看着像"不自信"但其实已经"决定"了。`max_proba` 和 `margin` 的组合判断能识别出"模型自己也拿不准"的情况，强制推给 LLM 二次确认。

**Stage 2 的 predict/proba 错位修复**：训练时 LabelEncoder 编码空间断裂（16+ 变体），LogisticRegression 的 `classes_` 不连续，直接用 `predict` 返回值当 `predict_proba` 列索引会越界。修复后重训使 LabelEncoder 干净，宏 F1 从 0.674 提升到 0.93。

**输出**：`ClassifiedMessage`，包含一级、二级标签、置信度、分类来源、判定依据。

### 3.5.5 分类器自进化模块 (Auto-Evolution)

#### 设计理念

采用"大模型知识蒸馏 + 大模型作裁判"架构：
- **LLM = 老师**：负责标注高质量训练数据（实时蒸馏）和复核学生作业（LLM-as-a-Judge）
- **Embedding分类器 = 学生**：处理海量日常任务（低成本、低延迟）

#### 组件详细设计

##### 3.5.5.1 银标数据收集器（实时蒸馏）

**触发时机**：消息经过LLM兜底分类（FR-CLF-03）且输出明确

**收集条件**：
- LLM输出无含糊其辞
- 给出了强有力的判断依据
- 标签置信度评估为高

**数据格式**：
```python
{
    "text": "原始文本",
    "label": "LLM给出的标签",
    "reasoning": "LLM的推理链",
    "source": "llm_fallback",
    "timestamp": "收集时间"
}
```

**Chain-of-Thought要求**：LLM打标时需先输出判定理由，最后再输出JSON标签

##### 3.5.5.2 错题本收集器（LLM-as-a-Judge）

**运行机制**：
- 运行时间：每日凌晨空闲时段
- 抽样比例：1%（从前两层高置信度通过的消息中随机抽样）
- 裁判模型：使用能力最强的模型（GPT-4o/Claude 3.5 Sonnet），不用处理日常任务的小模型

**复核流程**：
```
每日凌晨
    ↓
从高置信度通过消息中随机抽样1%
    ↓
发送至LLM进行重判
    ↓
对比LLM判定与原分类结果
    ↓
不一致 → 记录错误特征，LLM结果作为正确标签存入错题本
一致 → 无操作
```

##### 3.5.5.3 对抗样本生成器（长尾增强）

**触发条件**：某些罕见黑产类型缺乏训练数据

**生成流程**：

```
识别稀有类别（如"非法举报"变种）
    ↓
向LLM提供少量现有样本
    ↓
下达指令："请模拟黑产分子的语气，生成50条类似但表达不同的黑话文本"
    ↓
合成数据自动混入训练素材库
```

**数据平衡**：解决稀有类别数据不足的问题

##### 3.5.5.3-bis slang→rule 自动桥接（2026-06-05 V2 新增, commit `329471d`）

**背景**：V1 阶段 `slang_learning` 状态机推进到 `CONFIRMED` 后只入库 `slang_mappings` 表供检索，但 Stage 1 规则关键词永远硬编码在 `pipeline/classifier.py:DEFAULT_RULES` 中。CONFIRMED slang 不会自动反哺 Stage 1，导致规则系统永远落后于实际黑产演化。

**桥接流程**：

```
SlangCandidate.status == 'CONFIRMED'
    ↓
SlangToRuleBridge.evaluate_batch(batch_size=20)
    ↓ (LLM 评判)
约束 Prompt: "判断这个暗语是否适合作为某 level1 类别的关键词"
   • suitable=true/false
   • level1 + level2
   • keywords: ["出号", "出🐭", ...]  ← 纯文本, 禁 regex 元字符
   • confidence
    ↓ (Embedding 双重校验)
Classify meaning via embedding → emb_level1 + emb_conf
   • emb_conf >= 0.7
   • emb_level1 == llm_level1
    ↓
双校验通过 → 写入 antiblack.dynamic_rules
            → 下次 Classifier.classify_batch 加载新规则
```

**数据库表**：

| 表名 | 用途 |
|---|---|
| `antiblack.dynamic_rules` | 桥接产出的规则 (rule_id, level1_label, level2_label, keywords JSONB, hit_count, correct_count, is_enabled) |
| `antiblack.slang_evaluations` | 桥接去重缓存 (slang_candidate_id, eval_status, eval_json) |

**防御性 ReDoS 设计**：

LLM 生成的 `keywords` **只允许纯文本子串**（禁 `*+?{}[]()|^$.` 等正则元字符），通过 `_is_safe_keyword()` 过滤后写入 `dynamic_rules.keywords`。Stage 1 匹配走 `pattern in text.lower()` 路径（O(N) substring match），**不走 Aho-Corasick 的 regex 路径**，无回溯风险。

**成本控制**：

- 攒批：每 20 个 CONFIRMED slang 一次性 LLM 调用
- 频率限制：每天最多 2 批（防止 LLM 配额爆炸）
- 缓存：已评估过的 slang 写入 `slang_evaluations` 表，不再重复评估

**回滚机制**：

每周统计 dynamic rule 命中率（correct_count / hit_count）：
- hit_count >= 50 且 hit_rate < 0.4 → 自动 `is_enabled = FALSE`
- 防止 LLM 幻觉或 embedding 误判产生的"垃圾规则"长期占用 Stage 1

**对应代码**：`pipeline/slang_to_rule_bridge.py` (class `SlangToRuleBridge`)

**生成流程**：

```
识别稀有类别（如"非法举报"变种）
    ↓
向LLM提供少量现有样本
    ↓
下达指令："请模拟黑产分子的语气，生成50条类似但表达不同的黑话文本"
    ↓
合成数据自动混入训练素材库
```

##### 3.5.5.4 新型类别自动发现（Category Discovery，2026-06-05 V2 已实现）

###### V2 完整流水线（commit `329471d`）

```
未知/其他样本 (近 7 天) 
    ↓
[1] Ollama bge-m3 1024D embedding
    ↓
[2] UMAP 降维 (1024D → 10D, n_neighbors=15, metric=cosine)
    • 模型持久化 → umap_unknown_discovery.pkl
    • 支持 transform() 增量推理
    ↓
[3] HDBSCAN 聚类 (min_cluster_size=30)
    ↓
[4] 准入门槛 (cluster_size >= 50, 跨 3 天出现)
    ↓
[5] 中心采样 (Top 30 距质心最近样本)
    ↓
[6] 强约束 LLM 命名 (pipeline/prompts.py::build_cluster_naming_prompt)
    • System-Task-Rules-Output 4 段结构
    • 4 条硬规则: 优先归类 / 高度抽象 / 2-6 汉字 / 无意义判 IRRELEVANT
    ↓
[7] 代码级三道断言
    ① 长度: proposed_level2 ∈ [2, 6] 汉字
    ② 置信度: confidence >= 0.8
    ③ 类别: is_new_category=true
    ↓
[8] 候选池去重 (与 taxonomy + pending_category_proposals 余弦相似 > 0.85 归并)
    ↓
[9] 写入 antiblack.pending_category_proposals
    ↓
[10] 人工审核 (status: pending → approved/rejected/merged)
```

**为什么必须 UMAP 降维**（V1 的设计缺陷）：

1024 维直接做 HDBSCAN 会遭遇**维数灾难**——任意两个随机点的距离趋于一致，到处都是绝对稀疏，HDBSCAN 找不到密度差异。UMAP 在保留局部+全局拓扑的同时降到 10 维，让 HDBSCAN 能正常工作。**降维到 2-3 维仅用于画散点图给人看，会挤压不相关类别破坏聚类结构**。

**LLM 强约束 Prompt 4 段结构**（V1 → V2 的关键升级）：

V1 直接问"这是什么类别？"——LLM 容易发散（"微信朋友圈卖高仿劳力士手表"）。V2 用 System-Task-Rules-Output 4 段强约束 Prompt + 代码级三道断言，强制 LLM 给出"账号买卖"这种抽象 2-6 字命名。

**候选池去重（防类别爆炸）**：

LLM 可能星期一发明"跑分洗钱"，星期二对另一个相似簇发明"代收代付"——本质是同一类。V2 用余弦相似度查重：与现有 taxonomy 或 pending_category_proposals 池相似 > 0.85 时，把当前簇样本**追加**到现有候选簇，不产生新工单。

**性能优化路径**（候选池规模增长时）：

| 规模 | 实现 | 复杂度 |
|---|---|---|
| < 1000 | NumPy 矩阵乘法 | $O(N)$ |
| 1000-10000 | 预计算 + batch dot product | $O(N \cdot d)$ |
| > 10000 | PostgreSQL pgvector + IVF 索引 | 亚毫秒级 |

**对应代码**：`pipeline/unknown_discovery.py` (class `UnknownDiscovery.run()`) + `pipeline/prompts.py` + `migrations/phase2_init.sql`。

**详细工作流 + 参数表 + 验证结果**见 `docs/新黑产类别自动发现规划.md`（已更新为 V2 已实现状态）。

### 3.6 分流决策与抽取模块组

这是整个架构实现三角平衡的核心。由一个分流决策器和两个处理通道组成。

#### 3.6.1 分流决策器

**位置**：主控Agent的一部分，但逻辑上紧密耦合于抽取前。

**输入**：`ClassifiedMessage` + 消息元数据。

**价值计算算法**：
```
Score =
  w1 * RiskLevel(高风险=1, 中=0.5, 低=0)
+ w2 * EntityDensity(预检测实体数量归一化)
+ w3 * SemanticComplexity(黑话词命中数/文本长度)
+ w4 * Novelty(与近期消息的SimHash最小距离归一化)
+ w5 * SourceAuthority(核心群组=1, 普通=0.5)
```
权重可配置，默认`w1=0.3, w2=0.2, w3=0.2, w4=0.15, w5=0.15`。

**决策逻辑**：
- 若 `Score >= 阈值`（默认为0.6），则路由至**图谱构建通道**。
- 否则路由至**轻量通道**。
- 阈值可根据当前Token余量动态调整：余量 < 30%时，自动上调阈值至0.7。

**查询超时机制**：
- 用户查询时启动采集任务，设置超时时间（默认30秒）
- 超时则返回已处理数据，后台继续处理未完成任务
- 主控Agent同时执行采集和数据库读取，并行处理提高响应速度

#### 3.6.2 轻量通道处理器

**运行环境**：纯本地，不消耗任何LLM Token。

**处理步骤**：
1. **正则抽取**：预编译正则库，提取手机号、微信号、QQ号、URL、邮箱、金额等。
2. **词典抽取**：基于AC自动机，匹配黑话词典，输出原文和标准词映射。
3. **平台标识提取**：关键词命中识别”抖号/头条/快手”等，作为实体属性。
4. **结构化组装**：生成`BasicEntityRecord`，直接写入基础实体数据库。

**性能目标**：单条消息处理时间 < 5ms。

#### 3.6.3 图谱构建通道（LightRAG + VLM多模态）

**运行环境**：本地部署LightRAG引擎和VLM，内部调用LLM/VLM API。

**处理步骤**：
1. **上下文增强**：将轻量通道的初步抽取结果（如已识别微信号）拼接入文本，格式如`[已知:微信=xxx] 原文...`。
2. **LightRAG `ainsert` 调用**：传入增强文本。
   - 内部LLM调用：实体抽取、实体消歧、关系抽取。
   - 实体存储为图谱节点，关系存储为边，向量化实体描述存入向量索引。
3. **Token统计与监控**：记录此次调用消耗的Token数，更新全局计数器。
4. **新知识反馈**（可选）：LightRAG完成后，可查询新生成/更新的节点和边，若发现新的黑话映射或强关联，可异步上报至规则管理模块，纳入轻量通道词典。

**VLM多模态处理**（图片专项）：
- 图片进来后先走OCR+正则，命中高价值实体则直接入库，**跳过VLM**
- 未命中的图片进入VLM分析：生成语义描述 + 结构化JSON实体
- VLM输出拼接入LightRAG，构建多模态知识图谱
- 新发现的套路图片自动上报黑库，下次命中直接复用结论

**并发控制**：图谱构建通道采用独立的工作池处理，池大小可配置（建议1-3），避免LLM API过载。

### 3.7 查询与报告模块

**角色**：响应用户的最终查询，从基础实体库和LightRAG图谱中检索，组装为可理解的结果。

**查询处理流程**：
1. **解析用户查询参数**：从主控Agent获取意图解析结果（时间、风险类型、平台、关键词等）。
2. **基础检索**：向基础实体数据库发起结构化查询，获得匹配的`BasicEntityRecord`列表。
3. **图谱关联查询**：提取基础结果中的核心实体（如微信号、手机号），调用LightRAG的本地查询接口，执行一跳或多跳遍历，获取关联的其他实体和关系。
4. **线索聚合与排序**：将基础信息与图谱信息聚合，形成”线索”对象。可根据风险等级、关联实体数量、时效性进行排序。
5. **结果格式化**：生成用户友好的文本摘要或结构化展示，包含关键实体、关系、来源和判定依据。

**实体画像查询**：支持用户单独查询一个实体的全息画像，直接调用LightRAG的节点查询和图谱遍历功能，返回该实体的所有属性和关联网络。

### 3.8 黑话学习模块

**角色**：从情报数据中自动发现、学习新黑话，并生成可执行的正则表达式，供规则引擎实时过滤。跨通道运作，既服务于轻量通道的离线匹配增强，也为深度通道的图谱构建提供新知识输入。

**V2 增强（2026-06-05, commit `329471d`）**：新增 slang→rule 桥接（见 §3.5.5.3-bis），让 CONFIRMED slang 自动反哺 Stage 1 规则引擎，规则系统不再"永远是开局那批词"。

#### 3.8.1 模块架构

```
                    ┌─────────────────┐
                    │  黑话学习模块     │
                    │  SlangLearner    │
                    └────────┬────────┘
           ┌────────────────┼────────────────┐
           ↓                ↓                ↓
    轻量通道输出       深度通道图谱更新    批量验证
    (候选词发现)       (新实体检测)       (LLM推断)
           │                │                │
           └────────────────┴────────────────┘
                          ↓
              ┌───────────┴───────────┐
              ↓                       ↓
       AC自动机词典(热更新)      LightRAG图谱
```

#### 3.8.2 核心组件

| 组件 | 职责 | 消耗资源 |
|------|------|----------|
| **SlangCandidateFinder** | 从轻量和深度通道的输出中发现未收录的候选黑话 | CPU（n-gram分析） |
| **SlangStatisticsTracker** | 追踪候选词的出现频次、上下文、首次/末次出现时间 | 内存/Redis |
| **SlangValidator** | 执行行为验证：regex_pattern测试 + 释义一致性比对 | Token（批量） |
| **SlangDictionarySyncer** | 将确认的黑话同步至AC自动机词典和正则规则库 | 网络/IO |

#### 3.8.3 递进式状态机

```
                     ┌──────────────────────────────────────────┐
                     ↓                                          │
NEW(1-5次) → OBSERVED(10次,触发第一次推断)                      │
                ↓ 验证失败(重试≤3次仍失败)   ↓ 验证成功          │
            REJECTED(30天静默期)            LIKELY(20次,第二次推断)
                ↓ (沉默期内 process_text 静默丢弃该词)            ↓ 60%回测通过 + 释义一致
                ↓ (静默期到期后若新语料继续累积 → 重新走 NEW)    ↓
                ↓                                            CONFIRMED → 写入词典+图谱
                ↓                                                 ↓ 出现500次
        ┌───────┴────────┐                                    STABLE(不再推断)
        │  末位淘汰       │                                         │
        │  (CONFIRMED/   │                                         ↓
        │   STABLE →     │                              ┌────────────────────┐
        │   REJECTED)    │                              │ 末位淘汰(5%/200次)  │
        │  出现≥200 +     │                              │ 命中率<5% → REJECTED│
        │  命中率<5%     │                              └────────────────────┘
        └────────────────┘
```

**关键**：状态跃迁由**验证结果**驱动，而非仅靠出现次数。

**重试机制**：验证失败后反馈给LLM重新生成regex_pattern，最多重试3次；3次都失败则REJECTED + 30天静默期。`slang_mappings` 中对应条目硬删除，`slang_candidates.reject_until` 写入静默截止时间。

**退役机制**（末位淘汰）：CONFIRMED/STABLE 词若**出现 ≥200 次且命中率 <5%**（参见 3.8.9），由 `eliminate_weak_slangs()` 周期任务打入 REJECTED + 30 天静默期，避免死词长期占用 AC 自动机词典。

**沉默期防回流**：静默期内的 REJECTED 词在 `process_text` 入口被静默丢弃（不入 candidate、不增计数、不重新入 mapping），防止 30 天后再次撞到阈值触发"复活循环"。daemon 重启后 `_load_candidates_from_db` 仍能恢复 `reject_until`。

**说明**：考虑到情报数据量大，触发阈值设置较高，避免过多LLM调用。

#### 3.8.4 行为验证机制（核心）

**摒弃**：LLM输出的`confidence`分数（未经校准、不可靠）

**采用**：系统自动执行客观测试，分三层闸门把关：

**第一层 — LLM 自检（白盒对抗）**：
- LLM 需生成 `regex_pattern` + 2 个正例 + 2 个对抗性负例
- 对抗性负例**必须包含候选词核心字眼、但语境完全日常合法**（如候选词为"种草"，负例必须是"我在阳台种草"，不能是"今天天气好"）
- 系统自动执行匹配测试：**正例全部命中，负例一个都不命中**才算 LLM 自检通过

**第二层 — 释义一致性（黑盒语义）**：
- 提取 `meaning` 中的核心词（2 字以上中文）
- 在 contexts_sample（最后 10 条独立上下文）中检查这些核心词的出现率
- **通过条件**：核心词在 ≥80% 上下文里出现（过滤掉 LLM 强行编造含义）

**第三层 — 真实回测（held-out backtest，60% 阈值）**：
- 取剩余约 40 条独立真实上下文（前序消息，未发给 LLM）
- 用 LLM 生成的 `regex_pattern` 在这 40 条语料上做命中率测试
- **通过条件**：命中率 ≥ 60%
- 低于阈值直接拒绝（计入 `inference_count` 重试，达 3 次后 REJECTED）
- 这一层是真正的"防弱正则"机制——LLM 可能生成自造正例都过、但实战中匹配不到真实语料的伪正则

**样本来源（解决循环论证）**：

| 类型 | 来源 | 说明 |
|------|------|------|
| 触发正例 | 触发验证的那条消息 M1 | **不用于回测**（FR-SLANG-03 独立样本原则，避免循环论证） |
| LLM 自检正例 | LLM 自造的 2 个黑产语境短句 | 用于第一层 LLM 自检 |
| LLM 自检负例 | LLM 自造的 2 个对抗性短句 | 用于第一层 LLM 自检 |
| 回测集 | 同渠道其他包含 X 的消息（M2、M3...共约 40 条） | 用于第三层真实回测 |

**同渠道的重要性**：
- "飞机"在Telegram群组A中可能是黑话
- "飞机"在贴吧B中可能就是正常词汇（飞机票、飞机场）
- 必须按渠道分别统计和验证，不能跨渠道混用

**Prompt 设计**（三段式）：
1. **人设段**：黑产风控情报专家，**聚焦字节跳动旗下产品**（抖音 / TikTok / 头条 / 西瓜 / 飞书 / 豆包 / 剪映 等）
2. **核心防误判规则**：
   - 游戏名 / App名 / 星座名 → 不是黑话
   - 日常动词 → 不是黑话
   - **非字节系游戏账号交易**（三角洲 / 和平精英 / 王者荣耀 等腾讯系）→ `is_valid_slang=false`
   - **绝对拒绝类别**：内容标签 / 通用商务词 / 用户画像 / 文本截断碎片 / 平台官方词 / 反诈宣传词
3. **正则与对抗性样本规则**：要求 LLM 造"含候选词字眼、但完全日常合法"的负例
4. **emoji / 符号保留规则**（2026-06-02 增）：候选词若含 emoji（💰😈🔞👩‍💻 等），`refined_word` 和 `regex_pattern` **必须完整保留**，不可替换为文字描述。这些符号本身就是黑产规避审查的暗语组成。

完整 Prompt 见 `pipeline/slang_learning.py::_validate_candidate_with_llm`。

**emoji 端到端修复**（2026-06-02 增）：

旧版 `_extract_words` 用 `re.findall(r'[一-鿿]{2,8}', text)` 字符类不覆盖 emoji 块（U+1F300+ / U+2600+），emoji slang 在候选阶段就丢失。新版三路径捕获：

#### 3.8.8 末位淘汰与沉默期防回流

**目的**：黑产手法在变，但"曾经是黑话、现在已退场"的死词如果长期占据 AC 自动机词典，会拖累规则引擎并污染 LIKELY 队列统计。需要按命中率做末位淘汰。

**触发条件**（两个同时满足）：

| 条件 | 默认阈值 | 配置项 | 2026-06-02 调整 |
|------|---------|--------|----------------|
| 出现次数 | ≥ 200 (→ **100**) | `slang_learning.elimination.min_occurrences` | 沙盘显示 200 让 demote 对所有 14 个 CONFIRMED 都失效（最高 occ=122），降到 100 让机制真正生效 |
| 命中率（关联 `clues.slang_mappings` 命中数 ÷ occurrence_count） | < 5% | `slang_learning.elimination.min_hit_rate` | 沙盘 5%/7%/8%/10% 对当前数据都 ZERO 影响（瓶颈在 occ），保持 0.05 兜底 |

**执行流程**（`eliminate_weak_slangs()`，挂载在 daemon 的 `_slang_evolution_loop`）：

```
evaluate_slang_effectiveness() → List[(word, hit_rate)]
   ↓
demote_slangs(words)  // 单事务内：
   ↓   - UPDATE slang_candidates SET status='REJECTED', reject_until=NOW()+30d
   ↓   - DELETE slang_mappings WHERE slang_raw IN (words)
   ↓
seed_words 降级（与 promote_seed_word 对偶）：
   ↓   - demote_seed_word(words): UPDATE seed_words SET status='degraded'
   ↓     WHERE source='learned' AND status='active' AND word IN (words)
   ↓   - preset 来源（运维手工置入）不动，防止自动化流程误伤人工配置
   ↓
LightRAG 图谱节点清理（best-effort）：
   ↓   - delete_slang_entity(word) 链式调用 adelete_by_entity + adelete_entity_relation
   ↓   - 单 word 失败 try/except 隔离，整批失败仅 warning，不阻塞主流程
   ↓
同步本地 in-memory 状态（避免 _should_skip 失效）：
   ↓   - self._candidates[word].status = 'REJECTED'
   ↓   - self._candidates[word].reject_until = reject_until
   ↓   - self._known_words.discard(word)
```

**seed_words 降级**（与 `promote_seed_word` 对偶）：

CONFIRMED 的 slang 词在 `_persist_confirmed_slang` 阶段会通过 `promote_seed_word` 把自身升格为 `seed_words`（`source='learned'` + `status='active'`），让 MediaCrawler 后续按这些词拉取新语料。淘汰时必须同步降级，否则 MediaCrawler 会按 `status='active'` 持续拉取已被 REJECTED 的死词。

- `database.demote_seed_word(words)` 把 `source='learned' AND status='active'` 的词标为 `degraded`
- **业务安全底线**：`source` 过滤必须保留——preset 来源（运维手工置入的种子词）一律不动，防止自动化流程意外"降权"人工配置的规则
- 不直接 DELETE 行（保留 `weekly_hit_count` / `effective_clue_ratio` 等可观测指标用于事后分析）

**LightRAG 图谱节点清理**（2026-06-03 重写）：

**已废弃**：旧逻辑对每个 CONFIRMED 词调 `insert_custom_kg` 写入 Neo4j，末位淘汰时再 `delete_slang_entity` 清理。这种"slang-to-slang 锁"导致：
- 每天 5-10 次 LLM call（CONFIRMED slang 验证后写图谱）
- 每天 5-10 次 Neo4j 写
- 末位淘汰时双向维护链路
- 节点无业务关系（"黑话→释义"自包含文本，无共现边、无上下文）

**新逻辑**：
- CONFIRMED slang **不再写入** LightRAG，主存由 PG `slang_mappings` 表承担（已有 GIN 索引提供 hybrid 检索）
- 末位淘汰时**不再清理** LightRAG 节点
- `GraphProcessor.delete_slang_entity` 保留作为兼容接口（仅在 LightRAG 中仍存在该 slang 节点时调用），但实际不会被现有 slang_learning 流程触发
- LightRAG 专注于黑灰产图谱（`TOOL`/`TACTIC`/`TARGET`/`RESOURCE`/`INTENT`/`SCENE`/`PRICE` 节点），由 `MOExtractor` 驱动，详见 `docs/MO图谱设计.md`

**API 行为不变**：
- `GraphProcessor.delete_slang_entity(word)` 公开签名不变
- 内部从「链式调 `adelete_by_entity` + `adelete_entity_relation`」简化为「只调 `adelete_by_entity`」（后者是公开 API，**内部已经级联删实体 + entities_vdb 向量 + 所有以该实体为端点的边**，见 `LightRAG/lightrag/utils/utils_graph.py:66`；`adelete_entity_relation` 是内部 API，**不要直接调**）
- 单 word 失败由 `delete_slang_entity` 内部 try/except 隔离
- **Best-effort 语义**：图谱删除失败仅记 warning，不抛、不重试——避免图谱抖动阻塞 daemon

**沉默期防回流**（关键，防止 30 天后死循环）：

`demote_slangs` 把候选词打入 `REJECTED` + 硬删 `slang_mappings`，但 `slang_mappings` 是爬虫/分类器命中查询的入口。**硬删后若不拦截，同类语料触发 `process_text` 时，会因查不到 mapping 而把该词当作新词重新累加**，30 天沉默期一过，又撞到 50 次 → 又触发自学习 → 死循环。

**拦截点**：`process_text` 入口（`_should_skip` 已通过 `reject_until` 字段判断）+ daemon 重启后 `_load_candidates_from_db` 拉取 REJECTED 状态恢复 `reject_until`。

```sql
-- 数据库侧等价语义（仅供运维排查；运行时由 Python 内存过滤）
SELECT candidate_word FROM slang_candidates
WHERE status = 'REJECTED' AND reject_until > NOW();
```

**黑名单 TTL 复活机制**（2026-06-02 增，方案A）：

`config/slang_blacklist.py` 维护一份带 TTL 的硬黑名单。每个词有 `expires_at`（默认 90 天），过期后 `is_blacklisted()` 返回 False，词会重新流入 `_extract_words` → LLM 验证 → 60% 回测流程：

- **如果词仍是日常词**（如 `原创`）：LLM prompt 的硬拒绝规则会再次判 false，回测不通过 → 不会回到 CONFIRMED
- **如果词被黑产"征用"成了暗语**（历史上 `茶叶`/`喝茶`/`品茶` 从日常词演变成灰产代称）：会重新被捕获，验证后回到 CONFIRMED

持久化：`data/slang_blacklist_state.json`（进程重启不重置 TTL）。`scripts/cleanup_non_slangs.py` 清理时自动 `register_blacklist([word])` 加 TTL，避免清完又重新爬回。

**方案D — 双盲审计自动化复活**：放 Backlog，详见 `docs/backlog.md` Backlog-01。

**实战效果**（首轮末位淘汰）：
- 12 个生产噪声词被打入 REJECTED（"网名"、"红包"、"英语"、"微信号怎么改"等通用词，在 `clues` 里命中过几次但和黑产无关）
- 30 天静默期内，`process_text` 收到包含这些词的新语料时不会重新累加
- **第二轮强化**：补充 seed_words 降级 + LightRAG 图谱节点清理，避免下游拉取死词与 hybrid 检索污染

#### 3.8.10 硬黑名单（hardcoded blacklist）

**目的**：业务上明确"绝对不是黑话"的词，绕过 LLM 验证直接拦截。包括：内容标签（`原创`/`搞笑`）、通用商务词（`合作`/`报价`）、用户画像（`大学生`/`甜妹`）、平台官方词（`DOU+`/`蒲公英`）、反诈宣传词（`反诈骗`）、非字节系游戏（`三角洲租号`/`和平精英租号`）等。

**两层防护**：
1. **提取层过滤**（`pipeline/slang_learning.py::_extract_words`）：候选前 `is_blacklisted()` 拦截，不进入 LIKELY 队列
2. **LLM prompt 硬规则**（§3.8.4）：即使漏到 LLM 验证，prompt 注入 `HARDCODED_SLANG_BLACKLIST` 列表作为不可违反的硬规则

**TTL 复活机制**：见 §3.8.8 末段。每个词 90 天 TTL，过期后重新流入自然验证流程。

**维护接口**：
- `config.slang_blacklist._HARDCODED_WORDS`：静态词表（运营手工维护）
- `config.slang_blacklist.register_blacklist(words, ttl_days=90)`：动态注册（`scripts/cleanup_non_slangs.py` 清理时自动调用）
- `config.slang_blacklist.get_state_snapshot()`：当前活跃/过期词数（Grafana 埋点）

**Backlog 方案D — 双盲审计**：见 `docs/backlog.md` Backlog-01。

#### 3.8.9 ReDoS 防御

**问题**：LLM 在生成 `regex_pattern` 时可能产出灾难性回溯正则（如 `(a+)+$`、`(.*)+x`、`(a|a)+`），单次匹配即可挂死主线程数秒至数分钟，事件循环无法中断。

**约束**：CPython 的 `_sre` C 扩展**不释放 GIL**，因此 `concurrent.futures` 的 `future.result(timeout=...)` 不能中断正在执行的 `re.search`。所以线程池超时是**兜底**而非主防线。

**两层防御**（`SlangLearner._safe_regex_search`）：

| 层 | 机制 | 说明 |
|---|------|------|
| 主防线 | 启发式 ReDoS 检测（`_is_redos_unsafe`） | 拒绝嵌套量词 `(X+)+`、相邻量词 `a++`、量化的备选 `(a\|b)+` 三类典型结构。开销几乎为零，挡住 99% 的炸雷正则。 |
| 兜底 | 模块级 4-worker `ThreadPoolExecutor` + 0.5s 超时 | 在异常边界情况（如 LLM 生成新攻击变体）下，**单次匹配最长 0.5 秒后强制返回 None**。40 条回测总耗时上限 20 秒。 |

**模块级单例线程池**（关键）：
- 拒绝在每次调用时 `with ThreadPoolExecutor(...)` 创建/销毁（40 条回测串行时会被放大 40 倍线程切换开销）
- 全进程共享一个 4-worker 池，daemon 退出时 `atexit` 自动 shutdown

**配置**：
- `slang_learning.elimination.backtest_timeout_seconds = 0.5`（默认）
- **生产运维不允许把这个值调到 1s 以上**，否则 40 条回测可能拉长到 40s

## 4. 数据流详解

### 4.1 在线查询模式（用户发起查询）
```
用户 → 主控Agent(解析意图)
       → 采集模块(启动定向采集) ← 同时执行 →
       → 基础实体库读取（已有数据）
       → 消息队列
       → 清洗模块(标准化/去重)
       → 图片处理模块(OCR+正则 → 黑库匹配 → VLM按需)
       → 分类模块(规则→Embedding→LLM)
       → 分流决策
         ├─> 轻量抽取 → 写入Entity + MessageRef
         │          → 黑话学习模块(候选词发现)
         └─> 深度通道(LightRAG) → 写入Entity + MessageRef + LightRAG关系边
       → 主控Agent(等待处理完毕或超时30秒)
       → 返回已处理数据（未完成的后台继续）
       → 查询模块(从两库检索、聚合)
       → 用户(呈现线索列表)
```

**查询超时机制**：
- 超时时间默认30秒
- 超时则返回已处理数据，后台继续处理未完成任务
- 主控Agent同时执行采集和数据库读取，并行处理提高响应速度
       → 查询模块(从两库检索、聚合)
       → 用户(呈现线索列表)
```

**存储架构说明**：
- **基础实体库**：Entity（格式化实体）+ MessageRef（消息引用）+ SlangMapping（黑话映射）
- **LightRAG图谱**：Entity.entity_id引用（节点）+ 产业间关系（边）
- **系统目标**：识别"哪些产业可能连接在一起"，不追踪个人

**黑话学习模块数据流**：
```
轻量通道输出 → SlangCandidateFinder(发现未匹配词)
                        ↓
              SlangStatisticsTracker(统计频次)
                        ↓ 达到阈值
              SlangValidator(批量LLM验证 + regex测试)
                        ↓ 通过验证
              SlangDictionarySyncer(同步AC自动机+正则规则库)
                        ↓
              SlangMapping表写入 + LightRAG关系边写入(可选)
```

### 4.2 定时采集模式（调度器触发）
```
调度器(Airflow/Cron)每小时触发
  → 采集模块(增量采集: last_seen > 上次采集时间)
  → 消息队列
  → 清洗模块
  → 图片处理模块(OCR+正则 → 黑库匹配 → VLM按需)
  → 分类模块
  → 分流/抽取模块(轻量+图谱构建)
  → 写入Entity + MessageRef + LightRAG关系边
```

**增量采集策略**：
- 记录每个渠道的最后采集时间（last_collection_time）
- 下次采集只拉取 > last_collection_time 的消息
- 避免重复处理已入库的消息

该模式可独立运行，保证实体库的持续增长，也为在线查询提供即时的数据基础。

### 4.3 消息格式与存储演化

```
RawMessage → CleanedMessage → ClassifiedMessage
                                  │
                    ┌─────────────┼─────────────┐
                    ↓             ↓             ↓
               Entity +        ImageProcess   LightRAG
               MessageRef       Result        关系边
             (全量消息)      (含图片消息)   (仅深度通道)
```

**存储架构**：
| 存储 | 适用消息 | 内容 |
|------|----------|------|
| Entity + MessageRef | 所有消息 | 格式化实体（微信号、手机号、黑话映射） |
| LightRAG关系边 | 仅深度通道(<10%) | 产业间关联关系 |

**数据对象说明**：
- `ImageProcessResult`：图片处理结果，包含image_md5、ocr_text、entities（regex提取）、vlm_description（仅VLM分析后）、source标识。
- `SlangCandidate`：候选黑话，包含candidate_word、contexts、occurrence_count、status、regex_pattern（验证后）、verified。
- `LightRAG Edge`：产业间关系，如"账号交易 --使用--> 洗钱渠道"

### 4.4 黑话学习流程

```
时间线示例（以"飞机"为例）：
T+0min    消息1: "出抖号了，飞机加我"
          → AC自动机匹配，"飞机"未收录 → 创建候选词(NEW)
T+5min    消息2: "要的飞机来"
          → 候选词occurrence=2
... 持续累积 ...
T+30min   消息N: 第10次出现"飞机"
          → 状态NEW→OBSERVED，加入验证队列
T+31min   批量验证：LLM生成regex_pattern="(?i)飞机"
          → 系统执行独立样本测试：命中其他包含"飞机"的消息，不误伤随机负例
          → 释义一致性：高（与已知"飞机→Telegram"一致）
          → 状态OBSERVED→LIKELY→CONFIRMED
T+32min   同步到AC自动机词典 + 正则规则库 + SlangMapping表
T+33min   下一条消息到达："飞机优惠"
          → AC自动机匹配成功，识别为"Telegram"
```

**LightRAG图谱不存储黑话**：黑话映射存在SlangMapping表（基础实体库），LightRAG只存储产业间关联关系。

## 5. 并发与部署视图

### 5.1 Agent进程模型

每个Agent可设计为独立的进程或线程，通过消息队列或gRPC通信。在单机原型阶段，可采用协程（asyncio）的方式并发执行。

```
主进程 (Main)
  ├── OrchestratorAgent (协程)
  ├── CollectionModule (多协程, 每渠道独立)
  ├── CleaningModule (消费者协程组)
  ├── ImageProcessingModule (OCR+正则+VLM协程组)
  ├── ClassificationModule (消费者协程组)
  ├── LightExtractionModule (轻量通道协程组)
  ├── DeepAnalysisWorker (独立线程池, LightRAG+VLM调用)
  ├── SlangLearnerModule (黑话学习协程组)
  ├── AutoEvoAgent (定时协程, 自进化模块)
  └── QueryModule (按需协程)
```

消息队列作为纽带，使生产者和消费者协程解耦。

### 5.2 部署环境

- **开发/比赛原型**：单机部署，使用内存队列（如`asyncio.Queue`），SQLite/JSON文件作为基础实体存储，NanoVectorDB + NetworkX作为LightRAG后端。
- **生产扩展**：Kafka替代内存队列，MySQL/MongoDB替代文件存储，Milvus替代NanoVectorDB，分布式调度器（如Airflow）管理定时采集任务。

## 6. 关键技术选型总结

| 组件 | 技术选型 | 选型理由 |
|------|----------|----------|
| 消息队列 | Kafka (生产) / asyncio.Queue (原型) | 高吞吐、持久化、解耦 |
| 采集框架 | Telethon/MTProto (TG), Scrapy (通用) | 生态成熟，反反爬能力强 |

| 快速文本处理 | fastText, regex, AC自动机 | 本地化，零Token |
| 嵌入模型 | bge-small-zh (sentence-transformers) | 本地推理，速度快，中文友好 |
| 分类器 | XGBoost / 线性层 | 轻量，训练推理高效 |
| 图片OCR | Tesseract / PaddleOCR (本地) | 极低延迟，零Token，文字提取准确 |
| 视觉语言模型 | Qwen2-VL-2B (本地优先) / GPT-4o-mini (云端备选) | 轻量VLM本地部署零成本，云端仅作备份 |
| 黑产图片库 | MD5哈希索引 (SQLite/Redis) | 极低延迟比对，快速复用已知结论 |
| 知识图谱构建 | LightRAG (NanoVectorDB + NetworkX) | 原生支持图谱增量更新、向量检索、图遍历，契合实体消歧与关系挖掘需求 |

| 基础实体存储 | MongoDB (生产) / SQLite (原型) | 灵活结构，适合非固定字段的实体记录 |
| 接口协议 | REST / WebSocket (飞书Bot) | 易于集成 |

## 7. 关键设计决策与权衡

| 决策 | 权衡分析 |
|------|----------|
| **双通道而非全量LLM** | 成本：全量调用LLM费用不可控；时延：LLM推理延迟影响交互体验。双通道将99%的消息处理成本降至几乎为零，仅精华数据赋予图谱智能。 |
| **LightRAG而非从头构建图谱** | 图构建复杂度高，LightRAG封装了实体消歧和关系抽取的LLM调用逻辑，内部有成熟的向量-图融合机制，大幅降低开发成本。 |
| **异步离线图谱更新** | 在线查询对延迟敏感，图谱插入涉及多次LLM调用（≥3次），异步处理避免阻塞查询响应，并支持批量攒批优化。 |
| **规则优先于模型** | 黑产线索中存在大量格式化强特征（微信、手机号），规则处理精度高、零成本，是性价比最高的方式。模型仅补充泛化能力。 |
| **本地模型服务化** | Embedding和fastText本地部署，不受外部API限流和延迟影响，保障流水线稳定吞吐。 |
| **OCR优先+VLM按需** | 图片中大多数黑产信息是联系方式，OCR+正则已足够。VLM成本高，仅对OCR未命中且疑似黑产的图片触发，控制VLM调用量在5%以内。 |
| **黑库复用跳过VLM** | 已知的黑产图片直接复用已有分析结论，无需重复VLM分析。随着黑库扩充，VLM调用量可进一步降低。 |
| **行为验证替代LLM置信度** | 黑话判定不以LLM自我评分为准，而以regex_pattern测试结果为准。不依赖未经校准的置信度，确保结果可验证。 |
| **递进式学习控制成本** | 出现10次才触发第一次LLM推断，20次才第二次，高阈值避免大量LLM调用。行为验证（regex测试）本地执行，零Token。 |
| **独立样本+统计采样** | 正例来源于独立消息而非触发消息，负例来源于随机采样而非人工确认。避免循环论证和人工依赖，纯自动化。 |
| **LLM重试机制** | regex验证失败时不直接REJECT，而是反馈给LLM重新生成，最多重试3次。提高鲁棒性，避免因单次生成质量差而误杀。 |
| **两库分离架构** | 基础实体库存格式化实体（微信号、手机号、黑话映射），LightRAG存产业关联关系。两库分工明确：实体检索→图谱关联→产业网络揭示。LightRAG节点为Entity引用，非重复存储。 |
| **情报分析而非个人追踪** | 系统目标是识别"哪些产业可能连接在一起"，不追踪个人。LightRAG存储产业间关系（如账号买卖↔洗钱），提供网络线索而非个人结论。 |
| **消息级容错策略** | 失败消息直接丢弃（不重试，不进入死信队列），错误日志记录供事后分析。简化系统复杂度，保证主流程不阻塞。 |
| **API接口降级策略** | 主API（DeepSeek）失败/超时3秒后自动切换备用API（Qwen→OpenAI兼容接口）。多接口备用保证系统可用性。 |
| **图片下载容错** | 下载失败自动重试3次（间隔1秒、2秒、4秒），仍失败则记录错误日志并跳过。不阻塞主流程。 |
| **定时采集调度** | 调度器（Airflow/Cron）每小时触发采集任务，基于last_seen时间戳实现增量采集，避免重复处理已入库数据。 |

## 8. 架构演进路径

- **比赛交付版**：单机全内存运行，asyncio调度，SQLite+LightRAG，重点展示双通道和自然语言交互。
- **准生产版**：引入Kafka、分布式采集、基础实体库改为MongoDB，支持持续采集和更大规模数据。
- **企业级版**：全量微服务化，采集/清洗/分类/抽取均独立部署，图谱存储升级为JanusGraph或Neo4j，对接公司内部风控规则引擎，形成闭环对抗体系。
