# 黑灰产情报分析Agent系统架构设计文档

**版本**：V1.0  
**对应需求文档版本**：V1.0  
**设计目标**：定义系统的高层结构、组件划分、数据流转、通信机制和关键技术选型，确保系统满足功能和非功能需求，尤其在效果、成本、时延三角约束下实现最优平衡。

---

## 1. 架构设计原则

| 原则 | 说明 |
|------|------|
| **管道-过滤器模式** | 数据流经采集→清洗→分类→抽取四道工序，每道工序独立、可替换、可并行水平扩展 |
| **双通道差异化处理** | 90%+的数据走规则化零Token轻量通道，<10%的高价值数据走LLM+图谱的图谱构建通道，实现成本控制与深度分析统一 |
| **异步解耦** | 采集与处理通过消息队列解耦，LightRAG图谱构建可异步离线执行，不影响实时响应链路 |
| **Agent化编排** | 每个核心处理环节封装为独立Agent，由主控Agent调度，支持自然语言任务解析和流程组合 |
| **本地优先** | Embedding分类、文本处理等高频操作全部本地化，仅关键语义理解、图谱构建调用远端LLM，最小化外部依赖和延迟 |
| **可解释性内建** | 分类和实体抽取结果携带证据和来源，图谱关系可追溯，满足情报分析的可信度要求 |

---

## 2. 总体架构概览

系统采用**分层解耦**架构，从下至上划分为基础设施层、数据处理层、业务逻辑层和交互层，层与层之间通过明确的接口通信。

**各层职责**：

- **交互层**：提供用户输入查询的界面，将自然语言请求转发至主控Agent，并将最终结果格式化呈现。
- **业务逻辑层**：主控Agent作为大脑，负责解析意图、生成任务计划、调度流水线中的各个模块，并在处理过程中做出关键分流决策。查询/报告模块则专门负责从实体库中检索并组装最终答案。
- **数据处理层**：包含采集、清洗、意图分类、实体抽取等独立的处理模块，每个模块完成一个单一环节。它们由主控Agent调用，也可以被编排为自动运行的流水线（如定时采集、全量回溯）。
- **基础设施层**：提供数据持久化、消息传递、规则执行、模型推理等基础能力，是上层处理逻辑的支撑。

## 3. 核心组件详细设计

### 3.1 消息队列

**选型**：Apache Kafka（生产级推荐）或内存队列（原型验证）。

**作用**：
- 解耦采集与处理：采集模块高速写入原始消息，下游处理模块按自身节奏消费，避免数据源反压。
- 支持多消费者：清洗模块、归档服务等可独立订阅同一数据流。
- 削峰填谷：面对情报爆发期，消息堆积在队列中不丢失。

**消息主题设计**：
- `raw.messages`：原始消息主题，每条消息即为一个`RawMessage`对象。
- `cleaned.messages`（可选）：清洗后消息主题，用于后续分类模块消费。
- `deep.analysis.tasks`：图谱构建通道任务主题，存放高价值消息ID，供图谱构建通道处理。
- `image.analysis.tasks`：图片分析任务主题，存放需要VLM分析的图片信息，供图片处理模块消费。

### 3.2 图片处理模块

**角色**：对包含图片的消息进行低成本处理，提取结构化信息，并决定是否进入VLM分析。

**处理流水线**（两阶段过滤）：

#### 第一阶段：OCR优先处理
1. **图片下载与存储**：从RawMessage中提取图片URL/路径，下载并计算MD5哈希，存储到本地或对象存储。

   **图片下载容错**：下载失败时自动重试3次（间隔1秒、2秒、4秒），仍失败则记录image_url、error_msg、timestamp到错误日志，跳过该图片不阻塞主流程。

2. **OCR文字提取**：调用本地OCR（Tesseract/PaddleOCR）提取图片中的文字内容。
3. **正则结构化提取**：对OCR输出立即执行正则匹配，提取手机号、微信号、QQ号、URL、邮箱等高价值实体。
4. **黑库快速匹配**：将图片MD5与黑产图片样本库比对。命中则复用已知结论，**跳过VLM分析**。

#### 第二阶段：VLM分析（按需）
仅对以下条件同时满足的图片触发：
- OCR未提取到高价值实体
- 图片MD5未命中黑库
- 消息整体评分达到图谱构建通道阈值

5. **VLM语义描述生成**：调用本地轻量VLM（Qwen2-VL-2B）或云端VLM，生成图片语义描述。
6. **VLM结构化提取**：要求VLM以JSON格式输出实体列表。
7. **多模态文本融合**：将VLM描述拼接到消息文本，格式如`[图片语义] xxx`。
8. **新黑产图片上报与审核**：若VLM发现新型黑产套路截图，上报至审核队列。审核Agent（独立于VLM处理流程，作为第三者确保公平性）消费队列并执行二次确认。审核通过后写入黑库，下次同类图片可跳过VLM直接处理；审核不通过则记录日志后丢弃。

**Token消耗控制策略**：
- 优先使用本地轻量VLM，仅在本地模型不可用时调用云端API
- 设置单图Token上限（max_tokens=500）
- VLM调用量控制在图片总量的5%以内

**API接口降级策略**：
- 主API：DeepSeek
- 备用API1：Qwen（如主API失败/超时3秒）
- 备用API2：OpenAI兼容接口（如备用API1也失败）
- 所有API均失败时，记录错误日志，标记该消息为FAILED

**输出**：`ImageProcessingResult`对象，包含：image_md5、ocr_text、entities（regex提取的实体）、vlm_description（仅VLM分析后）、source（regex/ocr/vlm）、priority（high/low）

### 3.3 采集模块

**角色**：情报源适配器，负责从多源渠道抓取消息，并转换为统一格式写入消息队列。

**内部结构**：
- **渠道适配器管理器**：维护一个适配器列表，每个适配器实现统一接口：`start(keywords, time_range)`、`stop()`、`get_status()`。
- **TG适配器**：基于Telegram官方客户端库实现，支持文本消息、图片描述等。
- **通用Web适配器**：基于Scrapy或Requests实现，带IP代理池和频率控制。
- **格式化器**：将渠道特定数据转换为统一的`RawMessage` Schema。

**关键行为**：
1. **接收主控Agent下发的采集任务**（渠道、关键词、时间窗）。
2. 启用对应适配器执行定向采集。
3. 对抓取到的每条消息，即时格式化并发送至`raw.messages`主题。
4. 上报采集进度和状态。

### 3.4 清洗模块

**角色**：从`raw.messages`消费原始消息，执行标准化、去重、过滤，产出洁净消息流。

**处理流水线**（管道模式）：
1. **格式标准化器**：HTML标签剥离、Unicode规范化、全半角转换、emoji转文字描述。
2. **精确去重器**：计算文本MD5，与内存中的布隆过滤器+LRU缓存比较，24小时窗口。
3. **近似去重器**：SimHash计算与滑动窗口内的历史指纹比较，汉明距离≤3判定重复。
4. **噪声过滤器**：规则引擎（正则）剔除纯表情、纯符号、常见系统通知等。
5. **语言检测器**：调用本地fastText模型，标注语种并过滤非目标语言。

**输出**：`CleanedMessage`对象，写入`cleaned.messages`主题，或直接内存传递给分类模块（取决于部署模式）。

### 3.5 意图分类模块

**角色**：判断消息的风险类型，提供多级标签和置信度。

**分类器链**（责任链模式）：
1. **规则分类器**：基于强特征词匹配，命中则直接返回高置信度标签。规则库结构为`(关键词/正则) → (一级标签, 二级标签, 置信度)`。
2. **Embedding分类器**：利用本地部署的`sentence-transformers`模型将文本向量化，通过一个预训练的轻量分类头（如线性层或XGBoost）给出标签和置信度。
3. **LLM分类器**：作为兜底，仅在规则和Embedding均低置信度时调用。Prompt包含完整标签体系定义和字节业务上下文，要求返回结构化JSON。

**标签体系管理**：标签体系独立维护，支持热加载。分类模块加载最新的标签映射，保证分类结果一致性。

**输出**：`ClassifiedMessage`，包含一级、二级标签、置信度、分类来源、判定依据。

### 3.5.5 分类器自进化模块 (Auto-Evolution)

#### 设计理念

采用"大模型知识蒸馏 + 大模型作裁判"架构：
- **LLM = 老师**：负责标注高质量训练数据（实时蒸馏）和复核学生作业（LLM-as-a-Judge）
- **Embedding分类器 = 学生**：处理海量日常任务（低成本、低延迟）

#### 组件详细设计

##### 3.5.5.1 银标数据收集器（实时蒸馏）

**触发时机**：消息经过LLM兜底分类（FR-CLF-03）且输出明确

**收集条件**：
- LLM输出无含糊其辞
- 给出了强有力的判断依据
- 标签置信度评估为高

**数据格式**：
```python
{
    "text": "原始文本",
    "label": "LLM给出的标签",
    "reasoning": "LLM的推理链",
    "source": "llm_fallback",
    "timestamp": "收集时间"
}
```

**Chain-of-Thought要求**：LLM打标时需先输出判定理由，最后再输出JSON标签

##### 3.5.5.2 错题本收集器（LLM-as-a-Judge）

**运行机制**：
- 运行时间：每日凌晨空闲时段
- 抽样比例：1%（从前两层高置信度通过的消息中随机抽样）
- 裁判模型：使用能力最强的模型（GPT-4o/Claude 3.5 Sonnet），不用处理日常任务的小模型

**复核流程**：
```
每日凌晨
    ↓
从高置信度通过消息中随机抽样1%
    ↓
发送至LLM进行重判
    ↓
对比LLM判定与原分类结果
    ↓
不一致 → 记录错误特征，LLM结果作为正确标签存入错题本
一致 → 无操作
```

##### 3.5.5.3 对抗样本生成器（长尾增强）

**触发条件**：某些罕见黑产类型缺乏训练数据

**生成流程**：
```
识别稀有类别（如"非法举报"变种）
    ↓
向LLM提供少量现有样本
    ↓
下达指令："请模拟黑产分子的语气，生成50条类似但表达不同的黑话文本"
    ↓
合成数据自动混入训练素材库
```

**数据平衡**：解决稀有类别数据不足的问题

##### 3.5.5.4 新型类别自动发现（Category Discovery）

**触发机制**：
- 当前两层分类器置信度低，且LLM兜底分类时频繁输出“未知”或不在预置体系内的自定义标签。
- 系统每日对“未知”样本的Embedding向量执行聚类分析（如 HDBSCAN）。
- 若发现高密度的新型样本簇，系统自动提取该簇的高频词和LLM生成的理由，向分析人员发送**“新风险类别提案”**。
- 人工确认后，该新类别正式加入标签库，并带着这批样本进入下一轮模型重训。

##### 3.5.5.5 模型重训与评估

**触发条件**：训练素材库规模达到阈值（默认2000条）

**重训流程**：
```
触发条件满足
    ↓
自动切分训练集与测试集（80%/20%）
    ↓
使用银标数据和错题本重训分类头
    ↓
构建隐藏测试集（含最新变种的真实数据）
    ↓
评估新模型：Macro F1提升 > 2% 且各类别Recall未断崖式下降
    ↓
通过 → 自动替换线上模型权重文件（无缝热更）
失败 → 保留当前模型，记录失败日志
```

**无缝热更**：由于当前阶段为原型Demo，为了快速验证自进化链路，模型权重文件自动替换，全程无需人工干预。在未来生产环境中，将引入影子模式和人工卡点。

#### 防御性设计

| 策略 | 说明 |
|------|------|
| 高维打低维 | 日常任务用便宜小模型；异步抽检用最强模型（GPT-4o/Claude 3.5 Sonnet） |
| Chain-of-Thought | 要求LLM输出推理链，降低幻觉率 |
| 真实数据优先 | 隐藏测试集使用真实数据而非全合成数据 |

#### 与现有组件的交互

| 组件 | 交互方式 | 内容 |
|------|---------|------|
| LLM分类器(FR-CLF-03) | 读 | 读取LLM输出用于银标数据收集 |
| Embedding分类器 | 读/写 | 读取推理链；重训后写入新模型 |
| 训练素材库 | 读/写 | 读取历史数据；写入新样本 |
| 模型权重文件 | 写 | 重训后自动替换 |

### 3.6 分流决策与抽取模块组

这是整个架构实现三角平衡的核心。由一个分流决策器和两个处理通道组成。

#### 3.6.1 分流决策器

**位置**：主控Agent的一部分，但逻辑上紧密耦合于抽取前。

**输入**：`ClassifiedMessage` + 消息元数据。

**价值计算算法**：
```
Score =
  w1 * RiskLevel(高风险=1, 中=0.5, 低=0)
+ w2 * EntityDensity(预检测实体数量归一化)
+ w3 * SemanticComplexity(黑话词命中数/文本长度)
+ w4 * Novelty(与近期消息的SimHash最小距离归一化)
+ w5 * SourceAuthority(核心群组=1, 普通=0.5)
```
权重可配置，默认`w1=0.3, w2=0.2, w3=0.2, w4=0.15, w5=0.15`。

**决策逻辑**：
- 若 `Score >= 阈值`（默认为0.6），则路由至**图谱构建通道**。
- 否则路由至**轻量通道**。
- 阈值可根据当前Token余量动态调整：余量 < 30%时，自动上调阈值至0.7。

**查询超时机制**：
- 用户查询时启动采集任务，设置超时时间（默认30秒）
- 超时则返回已处理数据，后台继续处理未完成任务
- 主控Agent同时执行采集和数据库读取，并行处理提高响应速度

#### 3.6.2 轻量通道处理器

**运行环境**：纯本地，不消耗任何LLM Token。

**处理步骤**：
1. **正则抽取**：预编译正则库，提取手机号、微信号、QQ号、URL、邮箱、金额等。
2. **词典抽取**：基于AC自动机，匹配黑话词典，输出原文和标准词映射。
3. **平台标识提取**：关键词命中识别”抖号/头条/快手”等，作为实体属性。
4. **结构化组装**：生成`BasicEntityRecord`，直接写入基础实体数据库。

**性能目标**：单条消息处理时间 < 5ms。

#### 3.6.3 图谱构建通道（LightRAG + VLM多模态）

**运行环境**：本地部署LightRAG引擎和VLM，内部调用LLM/VLM API。

**处理步骤**：
1. **上下文增强**：将轻量通道的初步抽取结果（如已识别微信号）拼接入文本，格式如`[已知:微信=xxx] 原文...`。
2. **LightRAG `ainsert` 调用**：传入增强文本。
   - 内部LLM调用：实体抽取、实体消歧、关系抽取。
   - 实体存储为图谱节点，关系存储为边，向量化实体描述存入向量索引。
3. **Token统计与监控**：记录此次调用消耗的Token数，更新全局计数器。
4. **新知识反馈**（可选）：LightRAG完成后，可查询新生成/更新的节点和边，若发现新的黑话映射或强关联，可异步上报至规则管理模块，纳入轻量通道词典。

**VLM多模态处理**（图片专项）：
- 图片进来后先走OCR+正则，命中高价值实体则直接入库，**跳过VLM**
- 未命中的图片进入VLM分析：生成语义描述 + 结构化JSON实体
- VLM输出拼接入LightRAG，构建多模态知识图谱
- 新发现的套路图片自动上报黑库，下次命中直接复用结论

**并发控制**：图谱构建通道采用独立的工作池处理，池大小可配置（建议1-3），避免LLM API过载。

### 3.7 查询与报告模块

**角色**：响应用户的最终查询，从基础实体库和LightRAG图谱中检索，组装为可理解的结果。

**查询处理流程**：
1. **解析用户查询参数**：从主控Agent获取意图解析结果（时间、风险类型、平台、关键词等）。
2. **基础检索**：向基础实体数据库发起结构化查询，获得匹配的`BasicEntityRecord`列表。
3. **图谱关联查询**：提取基础结果中的核心实体（如微信号、手机号），调用LightRAG的本地查询接口，执行一跳或多跳遍历，获取关联的其他实体和关系。
4. **线索聚合与排序**：将基础信息与图谱信息聚合，形成”线索”对象。可根据风险等级、关联实体数量、时效性进行排序。
5. **结果格式化**：生成用户友好的文本摘要或结构化展示，包含关键实体、关系、来源和判定依据。

**实体画像查询**：支持用户单独查询一个实体的全息画像，直接调用LightRAG的节点查询和图谱遍历功能，返回该实体的所有属性和关联网络。

### 3.8 黑话学习模块

**角色**：从情报数据中自动发现、学习新黑话，并生成可执行的正则表达式，供规则引擎实时过滤。跨通道运作，既服务于轻量通道的离线匹配增强，也为深度通道的图谱构建提供新知识输入。

#### 3.8.1 模块架构

```
                    ┌─────────────────┐
                    │  黑话学习模块     │
                    │  SlangLearner    │
                    └────────┬────────┘
           ┌────────────────┼────────────────┐
           ↓                ↓                ↓
    轻量通道输出       深度通道图谱更新    批量验证
    (候选词发现)       (新实体检测)       (LLM推断)
           │                │                │
           └────────────────┴────────────────┘
                          ↓
              ┌───────────┴───────────┐
              ↓                       ↓
       AC自动机词典(热更新)      LightRAG图谱
```

#### 3.8.2 核心组件

| 组件 | 职责 | 消耗资源 |
|------|------|----------|
| **SlangCandidateFinder** | 从轻量和深度通道的输出中发现未收录的候选黑话 | CPU（n-gram分析） |
| **SlangStatisticsTracker** | 追踪候选词的出现频次、上下文、首次/末次出现时间 | 内存/Redis |
| **SlangValidator** | 执行行为验证：regex_pattern测试 + 释义一致性比对 | Token（批量） |
| **SlangDictionarySyncer** | 将确认的黑话同步至AC自动机词典和正则规则库 | 网络/IO |

#### 3.8.3 递进式状态机

```
NEW(1-5次) → OBSERVED(10次,触发第一次推断)
                ↓ 验证失败(重试≤3次仍失败)   ↓ 验证成功+多次出现
            REJECTED(30天静默期)            LIKELY(20次,第二次推断)
                                             ↓ 正则验证完美通过+高一致性
                                         CONFIRMED → 写入词典+图谱
                                             ↓ 出现500次
                                         STABLE(不再推断)
```

**关键**：状态跃迁由**验证结果**驱动，而非仅靠出现次数。

**重试机制**：验证失败后反馈给LLM重新生成regex_pattern，最多重试3次；3次都失败则REJECTED。

**不设置退役机制**：黑话一旦确认，长期有效（黑产词汇寿命通常很长）。

**说明**：考虑到情报数据量大，触发阈值设置较高，避免过多LLM调用。

#### 3.8.4 行为验证机制（核心）

**摒弃**：LLM输出的`confidence`分数（未经校准、不可靠）

**采用**：系统自动执行客观测试

**正则匹配验证**：
- LLM需生成`regex_pattern` + `test_cases`（正例+负例）
- 系统自动执行匹配测试
- **通过条件**：精准命中所有正例，且误伤率低于5%

**样本来源（解决循环论证）**：

| 类型 | 来源 | 说明 |
|------|------|------|
| 正例 | 同渠道其他包含X的消息（M2、M3...） | 候选词X在消息M1中被发现，M1为触发源不用于验证；从同渠道历史消息中搜索其他包含X的消息作为独立正例 |
| 负例 | 同渠道随机采样消息（约20条） | 不依赖人工确认；与候选词X无直接语义关联；误伤率阈值5% |

**同渠道的重要性**：
- “飞机”在Telegram群组A中可能是黑话
- “飞机”在贴吧B中可能就是正常词汇（飞机票、飞机场）
- 必须按渠道分别统计和验证，不能跨渠道混用

**释义一致性验证**：
- 同一候选词在多条消息中的LLM解析结果进行比对
- `meaning`高度一致（向量相似度>0.9）则可信度上升
- 多次不一致则标记为”多义词”，继续观察，暂不收录

#### 3.8.5 Token成本控制

| 策略 | 效果 |
|------|------|
| 统计预筛优先 | 先用词频筛选，LLM仅处理高置信候选 |
| 批量验证 | 积累10-20个候选词后一次性LLM调用 |
| 递进式触发 | 第10次出现才第一次推断，第20次才第二次 |
| 动态阈值 | Token余量<30%时，提高触发阈值 |
| 验证本地执行 | regex测试和一致性比对纯本地计算，零Token |

#### 3.8.6 图谱更新反馈触发条件

**触发条件**：

| 条件 | 说明 |
|------|------|
| 新实体发现 | LightRAG插入后返回新创建的节点 |
| 新关系发现 | LightRAG插入后返回新创建的边 |
| 置信度达标 | 新实体/关系的置信度 > 0.8 |

**反馈处理**：
```
触发条件满足
    ↓
反馈至规则管理模块
    ↓
新黑话 → 加入SlangMapping候选队列
新关系 → 更新关联分析结果
    ↓
可选择性地同步至AC自动机词典
```

#### 3.8.7 与现有组件的交互

| 现有组件 | 交互方式 | 内容 |
|----------|----------|------|
| AC自动机(FR-EXT-LIGHT-02) | 读/写 | 发现未匹配词作为候选；确认后更新词典 |
| LightRAG(FR-EXT-DEEP-02) | 读/写 | 读取已有黑话映射；写入新确认的黑话 |
| 轻量通道输出 | 订阅 | 获取BasicEntityRecord，发现未知词 |
| 深度通道输出 | 订阅 | 获取图谱更新结果，发现新实体 |

#### 3.8.8 数据模型

**slang_candidates（候选词表）**：
- candidate_word, contexts(JSON), occurrence_count, status, inference_count, reject_until

**SlangMapping（黑话映射表）**：
- mapping_id, slang_raw, meaning, regex_pattern, source(preset/learned), verified, confidence

**slang_learning_log（推断日志表）**：
- candidate_word, inference_step, llm_response, inference_result

**LightRAG关系边**：
- edge_id, source_entity_id(→Entity.entity_id), target_entity_id(→Entity.entity_id), relation_type(使用/供应/关联), confidence, evidence

## 4. 数据流详解

### 4.1 在线查询模式（用户发起查询）
```
用户 → 主控Agent(解析意图)
       → 采集模块(启动定向采集) ← 同时执行 →
       → 基础实体库读取（已有数据）
       → 消息队列
       → 清洗模块(标准化/去重)
       → 图片处理模块(OCR+正则 → 黑库匹配 → VLM按需)
       → 分类模块(规则→Embedding→LLM)
       → 分流决策
         ├─> 轻量抽取 → 写入Entity + MessageRef
         │          → 黑话学习模块(候选词发现)
         └─> 深度通道(LightRAG) → 写入Entity + MessageRef + LightRAG关系边
       → 主控Agent(等待处理完毕或超时30秒)
       → 返回已处理数据（未完成的后台继续）
       → 查询模块(从两库检索、聚合)
       → 用户(呈现线索列表)
```

**查询超时机制**：
- 超时时间默认30秒
- 超时则返回已处理数据，后台继续处理未完成任务
- 主控Agent同时执行采集和数据库读取，并行处理提高响应速度
       → 查询模块(从两库检索、聚合)
       → 用户(呈现线索列表)
```

**存储架构说明**：
- **基础实体库**：Entity（格式化实体）+ MessageRef（消息引用）+ SlangMapping（黑话映射）
- **LightRAG图谱**：Entity.entity_id引用（节点）+ 产业间关系（边）
- **系统目标**：识别"哪些产业可能连接在一起"，不追踪个人

**黑话学习模块数据流**：
```
轻量通道输出 → SlangCandidateFinder(发现未匹配词)
                        ↓
              SlangStatisticsTracker(统计频次)
                        ↓ 达到阈值
              SlangValidator(批量LLM验证 + regex测试)
                        ↓ 通过验证
              SlangDictionarySyncer(同步AC自动机+正则规则库)
                        ↓
              SlangMapping表写入 + LightRAG关系边写入(可选)
```

### 4.2 定时采集模式（调度器触发）
```
调度器(Airflow/Cron)每小时触发
  → 采集模块(增量采集: last_seen > 上次采集时间)
  → 消息队列
  → 清洗模块
  → 图片处理模块(OCR+正则 → 黑库匹配 → VLM按需)
  → 分类模块
  → 分流/抽取模块(轻量+图谱构建)
  → 写入Entity + MessageRef + LightRAG关系边
```

**增量采集策略**：
- 记录每个渠道的最后采集时间（last_collection_time）
- 下次采集只拉取 > last_collection_time 的消息
- 避免重复处理已入库的消息

该模式可独立运行，保证实体库的持续增长，也为在线查询提供即时的数据基础。

### 4.3 消息格式与存储演化

```
RawMessage → CleanedMessage → ClassifiedMessage
                                  │
                    ┌─────────────┼─────────────┐
                    ↓             ↓             ↓
               Entity +        ImageProcess   LightRAG
               MessageRef       Result        关系边
             (全量消息)      (含图片消息)   (仅深度通道)
```

**存储架构**：
| 存储 | 适用消息 | 内容 |
|------|----------|------|
| Entity + MessageRef | 所有消息 | 格式化实体（微信号、手机号、黑话映射） |
| LightRAG关系边 | 仅深度通道(<10%) | 产业间关联关系 |

**数据对象说明**：
- `ImageProcessResult`：图片处理结果，包含image_md5、ocr_text、entities（regex提取）、vlm_description（仅VLM分析后）、source标识。
- `SlangCandidate`：候选黑话，包含candidate_word、contexts、occurrence_count、status、regex_pattern（验证后）、verified。
- `LightRAG Edge`：产业间关系，如"账号交易 --使用--> 洗钱渠道"

### 4.4 黑话学习流程

```
时间线示例（以"飞机"为例）：
T+0min    消息1: "出抖号了，飞机加我"
          → AC自动机匹配，"飞机"未收录 → 创建候选词(NEW)
T+5min    消息2: "要的飞机来"
          → 候选词occurrence=2
... 持续累积 ...
T+30min   消息N: 第10次出现"飞机"
          → 状态NEW→OBSERVED，加入验证队列
T+31min   批量验证：LLM生成regex_pattern="(?i)飞机"
          → 系统执行独立样本测试：命中其他包含"飞机"的消息，不误伤随机负例
          → 释义一致性：高（与已知"飞机→Telegram"一致）
          → 状态OBSERVED→LIKELY→CONFIRMED
T+32min   同步到AC自动机词典 + 正则规则库 + SlangMapping表
T+33min   下一条消息到达："飞机优惠"
          → AC自动机匹配成功，识别为"Telegram"
```

**LightRAG图谱不存储黑话**：黑话映射存在SlangMapping表（基础实体库），LightRAG只存储产业间关联关系。

## 5. 并发与部署视图

### 5.1 Agent进程模型

每个Agent可设计为独立的进程或线程，通过消息队列或gRPC通信。在单机原型阶段，可采用协程（asyncio）的方式并发执行。

```
主进程 (Main)
  ├── OrchestratorAgent (协程)
  ├── CollectionModule (多协程, 每渠道独立)
  ├── CleaningModule (消费者协程组)
  ├── ImageProcessingModule (OCR+正则+VLM协程组)
  ├── ClassificationModule (消费者协程组)
  ├── LightExtractionModule (轻量通道协程组)
  ├── DeepAnalysisWorker (独立线程池, LightRAG+VLM调用)
  ├── SlangLearnerModule (黑话学习协程组)
  ├── AutoEvoAgent (定时协程, 自进化模块)
  └── QueryModule (按需协程)
```

消息队列作为纽带，使生产者和消费者协程解耦。

### 5.2 部署环境

- **开发/比赛原型**：单机部署，使用内存队列（如`asyncio.Queue`），SQLite/JSON文件作为基础实体存储，NanoVectorDB + NetworkX作为LightRAG后端。
- **生产扩展**：Kafka替代内存队列，MySQL/MongoDB替代文件存储，Milvus替代NanoVectorDB，分布式调度器（如Airflow）管理定时采集任务。

## 7. 关键设计决策与权衡

| 决策 | 权衡分析 |
|------|----------|
| **双通道而非全量LLM** | 成本：全量调用LLM费用不可控；时延：LLM推理延迟影响交互体验。双通道将99%的消息处理成本降至几乎为零，仅精华数据赋予图谱智能。 |
| **LightRAG而非从头构建图谱** | 图构建复杂度高，LightRAG封装了实体消歧和关系抽取的LLM调用逻辑，内部有成熟的向量-图融合机制，大幅降低开发成本。 |
| **异步离线图谱更新** | 在线查询对延迟敏感，图谱插入涉及多次LLM调用（≥3次），异步处理避免阻塞查询响应，并支持批量攒批优化。 |
| **规则优先于模型** | 黑产线索中存在大量格式化强特征（微信、手机号），规则处理精度高、零成本，是性价比最高的方式。模型仅补充泛化能力。 |
| **本地模型服务化** | Embedding和fastText本地部署，不受外部API限流和延迟影响，保障流水线稳定吞吐。 |
| **OCR优先+VLM按需** | 图片中大多数黑产信息是联系方式，OCR+正则已足够。VLM成本高，仅对OCR未命中且疑似黑产的图片触发，控制VLM调用量在5%以内。 |
| **黑库复用跳过VLM** | 已知的黑产图片直接复用已有分析结论，无需重复VLM分析。随着黑库扩充，VLM调用量可进一步降低。 |
| **行为验证替代LLM置信度** | 黑话判定不以LLM自我评分为准，而以regex_pattern测试结果为准。不依赖未经校准的置信度，确保结果可验证。 |
| **递进式学习控制成本** | 出现10次才触发第一次LLM推断，20次才第二次，高阈值避免大量LLM调用。行为验证（regex测试）本地执行，零Token。 |
| **独立样本+统计采样** | 正例来源于独立消息而非触发消息，负例来源于随机采样而非人工确认。避免循环论证和人工依赖，纯自动化。 |
| **LLM重试机制** | regex验证失败时不直接REJECT，而是反馈给LLM重新生成，最多重试3次。提高鲁棒性，避免因单次生成质量差而误杀。 |
| **两库分离架构** | 基础实体库存格式化实体（微信号、手机号、黑话映射），LightRAG存产业关联关系。两库分工明确：实体检索→图谱关联→产业网络揭示。LightRAG节点为Entity引用，非重复存储。 |
| **情报分析而非个人追踪** | 系统目标是识别"哪些产业可能连接在一起"，不追踪个人。LightRAG存储产业间关系（如账号买卖↔洗钱），提供网络线索而非个人结论。 |
| **消息级容错策略** | 失败消息直接丢弃（不重试，不进入死信队列），错误日志记录供事后分析。简化系统复杂度，保证主流程不阻塞。 |
| **API接口降级策略** | 主API（DeepSeek）失败/超时3秒后自动切换备用API（Qwen→OpenAI兼容接口）。多接口备用保证系统可用性。 |
| **图片下载容错** | 下载失败自动重试3次（间隔1秒、2秒、4秒），仍失败则记录错误日志并跳过。不阻塞主流程。 |
| **定时采集调度** | 调度器（Airflow/Cron）每小时触发采集任务，基于last_seen时间戳实现增量采集，避免重复处理已入库数据。 |

## 8. 架构演进路径

- **比赛交付版**：单机全内存运行，asyncio调度，SQLite+LightRAG，重点展示双通道和自然语言交互。
- **准生产版**：引入Kafka、分布式采集、基础实体库改为MongoDB，支持持续采集和更大规模数据。
- **企业级版**：全量微服务化，采集/清洗/分类/抽取均独立部署，图谱存储升级为JanusGraph或Neo4j，对接公司内部风控规则引擎，形成闭环对抗体系。
