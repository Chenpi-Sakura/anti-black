# 黑灰产情报分析Agent系统需求文档

**版本**：V1.0  
**面向领域**：字节跳动C端及B端产品风控  
**核心目标**：构建端到端自动化情报分析Agent，实现从多源数据采集到结构化实体库输出的完整链路，支撑业务从“人肉研判”走向“智能对抗”。

---

## 1. 系统概述

### 1.1 产品愿景

系统以自然语言交互方式接受分析人员的查询请求（如“查询近三天抖音账号买卖的线索”），自动完成**数据采集、清洗、意图分类、实体抽取、关联图谱构建**的全流程，最终输出**结构化、可解释、可操作的高质量风险线索**，并提供实体画像、关系溯源等深度分析能力。

### 1.2 核心价值

- 将散落在IM群组、论坛等多渠道的黑灰产情报，转化为结构化的作弊剧本和对抗方案。
- 利用大语言模型与知识图谱技术，解决黑话变种、隐蔽语义、实体关联等传统规则无法处理的问题。
- 通过”轻量规则+图谱构建通道”双通道架构，在效果、成本、时延之间取得平衡。

### 1.3 运行环境概述

系统采用**多Agent协作**架构，支持在单机或服务器环境运行。内部组件包括：
- 消息队列（Kafka/内存队列）
- 规则引擎
- 轻量NLP模型（Embedding）
- 大语言模型（API调用）
- LightRAG图存储引擎
- 基础实体库（关系型/文档型数据库）

## 3. 运行时功能需求（按处理流程）

### 3.1 系统启动与初始化

系统启动时需完成以下准备工作：

- **FR-INI-01 配置加载**：加载全局配置文件，包括但不限于：情报源列表及其凭证、采集频率、LLM API密钥与调用限额、各处理环节的阈值参数（相似度阈值、置信度阈值等）。
- **FR-INI-02 种子词库与规则加载**：从本地文件加载黑话词典、正则规则库、意图分类关键词库，加载至内存并构建AC自动机索引。
- **FR-INI-03 预置知识注入**：向LightRAG图谱中注入预置的黑话映射关系、平台别名、已知工具分类等静态知识（如`("飞机" → "Telegram")`），作为图谱的初始基座。
- **FR-INI-04 服务健康检查**：检测消息队列、数据库、LLM API、LightRAG引擎等组件的连通性，异常时给出明确提示。

- **FR-INI-05 系统冷启动与历史数据回填 (Backfill)**：
  - **分类模型冷启动（合成数据基线）**：为解决系统首日上线时轻量分类器无训练数据、导致请求全部透传打爆LLM的问题，系统在初始化阶段利用LLM基于预置分类体系**自动批量合成基线数据**。通过下发指令（如：“请生成500条模拟抖音账号买卖的黑话样本”），快速构造初始训练集，完成Embedding分类器的冷启动微调。
  - **预置黑名单冷启动**：首次启动时，系统通过脚本从企业内现有的风控黑名单（已知的黑产手机号、黑IP、被封禁设备库）中批量导入数据，作为基础实体库和图谱的孤立节点（基座）。
  - **历史回溯任务**：启动后，系统自动触发一次"长周期回溯采集"（如抓取Telegram核心群组过去30天的完整聊天记录，贴吧近3个月的精华帖），利用流水线全量处理一次，完成数据库的原始积累。
  - **服务就绪探针**：只有当历史回溯任务处理的数据量达到设定水位（如10,000条实体），且预置知识图谱构建完成后，主控Agent才将系统状态标记为`Ready`，正式对外提供查询服务。

### 3.2 用户交互与任务接收

- **FR-UI-01 自然语言查询接受**：系统提供交互界面（CLI/Web/飞书机器人），接受用户以自然语言输入的情报查询，如“查询近三天抖音账号买卖的线索”。
- **FR-UI-02 查询意图解析**：主控Agent解析用户查询，抽取出以下参数：
  - 时间范围（如“近三天”）
  - 风险类型（如“账号买卖”）
  - 目标平台（如“抖音”）
  - 其他约束（如“包含微信号”）
  解析过程可调用LLM辅助，但需控制Token消耗。
- **FR-UI-03 任务编排与反馈**：主控Agent根据解析结果生成任务计划，向用户反馈执行概览（如”正在从3个情报源采集数据，预计耗时2分钟”），随后调度下游Agent执行。

- **FR-UI-04 用户纠错与反馈闭环**：
  - **交互反馈界面**：在线索详情页提供一键反馈机制（如：”分类有误”、”实体提取错误”、”这是正常消息”）。
  - **数据纠偏与覆盖**：用户的纠错动作会立即触发数据库状态更新：修改基础实体库中的分类标签，撤销或修正LightRAG图谱中错误的边关系（软删除）。
  - **铂金样本入库**：系统将该条原始消息及用户的正确标签，标记为最高权重的`Platinum`级别，直接注入”自进化素材库”（FR-EVO-01）。
  - **对齐惩罚**：在触发下一次Embedding分类器重训（FR-EVO-03）时，`Platinum`样本被赋予10倍权重，强制模型向人工意图对齐。

### 3.3 数据采集

- **FR-COL-01 多源定向采集**：采集Agent根据查询参数中隐含的渠道（或默认全渠道）启动采集任务。至少支持以下渠道类型：
  - Telegram公开群组（通过API或公开链接）
  - 贴吧/论坛（通过合规爬虫）
  - 众包平台（可选）
- **FR-COL-02 关键词过滤采集**：支持根据种子词库进行定向采集（如只采集包含“抖号”“千粉”“新机”的消息），减少无关数据流入。
- **FR-COL-03 频率控制与反封禁**：每个渠道独立控制请求频率（如TG每个账号每秒不超过1次请求），支持多账号轮换和异常重试。
- **FR-COL-04 消息统一格式化**：将不同来源的原始消息转换为统一内部格式`RawMessage`，字段至少包括：消息ID、来源渠道、群组/版块ID、发布时间、作者ID、原始文本、原始HTML/富文本。
- **FR-COL-05 原始数据入队**：格式化后的`RawMessage`对象发送至消息队列，供下游消费。采集Agent只负责生产，不阻塞后续处理。

- **FR-COL-06 图片消息处理**：对包含图片的消息，需将图片下载并存储到本地或对象存储，生成图片的唯一标识（MD5哈希）。图片信息（路径/URL、MD5、采集时间）作为RawMessage的扩展字段保存，供下游图片处理模块消费。

- **FR-COL-07 图片黑产库匹配**：基于图片MD5与已知的黑产图片样本库进行快速比对。命中黑库的图片直接关联已知的分析结论（风险类型、标签），**跳过VLM分析环节**，降低成本。命中黑库的图片也标记为高优先级，确认为已知黑产后入库。黑库支持热更新。

- **FR-COL-08 定时采集任务**：系统支持调度器定时触发采集任务（默认每小时，可调节），采集模块根据关键词从指定渠道抓取消息。调度器可使用Airflow（生产环境）或Cron（原型验证）。

> **注意**：本系统**不包含**用户查询时实时触发AI采集的功能。数据采集完全由后台定时巡逻（FR-COL-08）完成，用户查询仅检索本地已采集的存量数据，以保证查询响应速度。

- **FR-COL-10 图片下载容错**：图片下载失败时自动重试3次（间隔1秒、2秒、4秒），仍失败则记录image_url、error_msg、timestamp到错误日志，跳过该图片不阻塞主流程。

- **FR-COL-11 种子词库动态扩展与衰减**：种子词库采用优先队列机制，支持动态更新：
  - **自动晋升**：当黑话学习模块将某个候选词状态标记为`CONFIRMED`，且该词在全盘数据中出现频次达到阈值（如>100次/周），系统自动将其加入采集种子词库，下发给采集Agent扩大监控面。
  - **热度衰减（TTL机制）**：为种子词库引入时间衰减机制。若某个种子词连续7天抓取回来的数据中"有效高风险情报"占比低于5%，系统自动将其降级，移出定向采集名单，避免浪费采集资源和API频率。

### 3.4 数据清洗

清洗Agent从消息队列消费`RawMessage`，执行以下顺序处理：

- **FR-CLN-01 格式标准化**：去除HTML标签、统一Unicode编码、全角半角转换、emoji保留并附加文本描述（如`:fire:`转为`[火焰]`），繁简统一为简体中文。
- **FR-CLN-02 精确去重**：基于消息内容计算MD5哈希，与24小时内的历史哈希池比对，完全一致的消息直接丢弃。
- **FR-CLN-03 近似去重**：对MD5未命中的消息，计算SimHash指纹，与滑动窗口内的历史指纹进行汉明距离比较，低于阈值（默认距离≤3）的视为重复，丢弃。
- **FR-CLN-04 噪声过滤**：通过规则剔除明显无意义的系统消息、纯表情刷屏、纯数字/符号串等。规则由正则表达式和长度/字符多样性阈值定义。
- **FR-CLN-05 语言检测**：调用fastText等轻量语言识别模型，标注消息语种（中文/英文/混合），非目标语种的消息可根据配置丢弃或降权。
- **FR-CLN-06 清洗后输出**：生成`CleanedMessage`对象，保留原始元信息，并将清洗后的文本传递至分类Agent。

- **FR-CLN-07 图片OCR预处理**：对包含图片的CleanedMessage，调用本地OCR（Tesseract/PaddleOCR）提取图片中的文字内容。提取结果附加到消息文本末尾，格式如`[图片文字] xxx`。OCR识别到的结构化信息（手机号、微信号、URL等）单独标记，供后续抽取模块使用。

- **FR-CLN-08 低成本结构化提取**：OCR输出后，立即用正则表达式提取联系方式。若提取到手机号/微信号/QQ号/邮箱等高价值实体，消息直接标记为高优先级，无需进入后续VLM分析环节，降低Token消耗。

- **FR-CLN-09 轻量图片分流**：对于OCR未提取到高价值实体但图片非空的消息，根据以下条件分流：
  - 图片MD5命中黑库 → 复用已知分析结论，标记高优先级，**跳过VLM分析**
  - 图片MD5未命中黑库 → 根据图片来源渠道、上下文综合判定，疑似黑产的进入图谱构建通道（VLM分析），其他降权处理或直接归档

### 3.5 意图分类

分类Agent接收`CleanedMessage`，完成风险意图判定。

- **预置分类体系（Taxonomy）**：系统初始基于业务经验预置标准化的分类标签，例如：`账号交易`（买卖/租借）、`流量作弊`（刷粉/点赞）、`诈骗引流`（刷单/杀猪盘）、`黑产工具`（接码/群控）、`未知/其他`。标签体系支持动态扩展。
- **FR-CLF-01 规则快速分类（第一层）**：基于强特征关键词和正则模式进行初筛。例如包含“出号”“换绑”的直接标记为`账号交易`；包含“点赞”“刷量”的标记为`流量作弊`。命中规则的消息赋予高置信度（>0.9），跳过后续模型分类。
- **FR-CLF-02 Embedding模型分类（第二层）**：对未命中规则的消息，使用本地部署的sentence-transformers模型（如`bge-small-zh`）进行向量化，再通过预训练的分类器（线性层/XGBoost）预测一级和二级风险类别，输出置信度。
- **FR-CLF-03 LLM兜底分类（第三层）**：对前两层置信度均低于阈值（默认<0.6）的消息，调用LLM API进行分类。Prompt中提供完整的分类选项和字节业务上下文，要求输出分类标签和判定依据。
- **FR-CLF-04 分类结果输出**：为每条消息生成`ClassifiedMessage`对象，包含：
  - 一级风险标签（如`账号交易`）
  - 二级风险标签（如`抖音号买卖`）
  - 置信度分数
  - 分类来源（`rule` / `model` / `llm`）
  - 分类依据（命中的关键词或LLM给出的理由）
- **FR-CLF-05 低风险消息处置**：对于分类为`正常/无风险`且置信度>0.8的消息，默认不进入后续抽取环节，可归档至低频查询库。

### 3.5.5 分类器自进化模块 (Auto-Evolution)

#### 设计背景

本模块取代传统的人工纠错机制，构建完全无人值守的分类器自进化闭环。采用"大模型知识蒸馏（Knowledge Distillation）+ 大模型作裁判（LLM-as-a-Judge）"架构：LLM作为"老师"负责标注高质量训练数据和复核学生（Embedding分类器）的作业，Embedding分类器作为"学生"处理海量日常任务（低成本、低延迟）。

#### FR-EVO-01 自动样本打标与收集（实时蒸馏）

- **触发条件**：消息经过FR-CLF-03（LLM兜底分类）处理且LLM输出明确分类标签（无含糊其辞，给出强有力的判断依据）
- **数据收集**：系统自动提取原始文本和LLM给出的标签，清洗后存入动态训练素材库
- **银标数据（Silver-standard data）**：该数据由LLM直接生成，标签置信度高，作为增量训练样本使用
- **Chain-of-Thought要求**：LLM打标时需先输出判定理由（如"该文本包含‘出号’字样，且附带价格，属于典型账号交易"），最后再输出JSON标签，降低幻觉率

#### FR-EVO-02 LLM异步抽检机制（LLM-as-a-Judge）

- **运行时间**：每日凌晨空闲时段自动运行
- **抽样范围**：从前两层（规则与Embedding）高置信度通过的消息中随机抽样1%
- **裁判模型**：使用能力最强的模型（如GPT-4o或Claude 3.5 Sonnet）进行复核，而非用于日常任务的小模型
- **复核结果处理**：
  - 若LLM判定与轻量分类器结果不一致，以LLM为准
  - 纠正后的数据记入"错题本"（纠错库）
  - 错题本数据可用于后续模型重训

#### FR-EVO-03 自动化模型重训与评估

- **触发条件**：增量样本库（包括银标数据和错题本）规模达到阈值（默认2000条）
- **重训流程**：
  1. 自动切分训练集与测试集
  2. 使用银标数据和错题本重训轻量分类头（XGBoost/MLP）
  3. 构建包含最新变种的隐藏测试集（使用真实数据而非全合成数据）
  4. 若新模型Macro F1分数提升超过2%且各类别Recall未出现断崖式下降，自动替换线上模型
- **无缝热更**：模型权重文件自动替换，全程无需人工干预

#### FR-EVO-04 长尾增强（对抗样本生成）

- **触发条件**：某些罕见黑产类型（如新型"非法举报"变种）缺乏训练数据
- **生成方式**：向LLM提供少量现有样本，下达指令"请模拟黑产分子的语气，生成50条类似但表达不同的黑话文本"
- **数据使用**：合成的对抗样本自动混入训练素材库，解决数据不平衡问题

#### 防御性设计：防止信息回音壁

- **高维打低维**：日常任务用便宜小模型，异步抽检用最强模型（如GPT-4o/Claude 3.5 Sonnet），保证教材质量
- **Chain-of-Thought**：要求LLM输出推理链，降低幻觉率，提升银标数据纯度
- **真实数据优先**：隐藏测试集使用真实数据而非全合成数据，避免LLM生成错误模式被当作ground truth

### 3.6 分流决策

主控Agent在每个`ClassifiedMessage`到达时，进行通道分流决策。

- **FR-ROU-01 分流条件判定**：根据以下维度综合计算消息的”图谱构建通道处理价值分”：
  - 风险意图明确度（高风险高置信 → 高分）
  - 实体密度（预检测到潜在实体数量多 → 高分）
  - 语义复杂度（黑话密度、文本长度 → 高分）
  - 新颖性（与近期消息不重复 → 加分）
  - 渠道权威性（来自核心群组 → 加分）
- **FR-ROU-02 阈值分流**：
  - 价值分 **低于阈值**：消息进入**轻量通道**（约占总量的90%+）。
  - 价值分 **高于阈值**：消息进入**图谱构建通道**（LightRAG处理，约占<10%）。
  阈值可配置，且支持根据当前Token余量动态调整（余量紧张时自动提高阈值）。

### 3.7 轻量通道：规则实体抽取与入库

适用于分流至轻量通道的消息，由抽取Agent执行。

- **FR-EXT-LIGHT-01 正则实体抽取**：使用预编译的正则表达式库抽取以下格式化实体：
  - 手机号（国内主流号段）
  - 微信号（常见格式）
  - QQ号
  - URL/短链
  - 邮箱地址
  - 价格金额（如“80元”“450/个”）
- **FR-EXT-LIGHT-02 词典匹配抽取**：利用AC自动机加载黑话词典，匹配并标注消息中的黑话变种词及其标准词映射（如“飞机→Telegram”）。
- **FR-EXT-LIGHT-03 平台标识识别**：通过关键词识别涉及的平台（如“抖号”“头条”“快手”），为实体添加平台属性。
- **FR-EXT-LIGHT-04 结构化记录组装**：将抽取结果与分类标签、原始消息元信息合并，生成`BasicEntityRecord`对象，字段至少包括：
  - 消息ID、采集时间、来源渠道、群组ID
  - 风险标签（一级、二级）
  - 抽取实体列表（手机号、微信、URL等，每个实体带有类型和值）
  - 匹配到的黑话映射列表
  - 原始文本（保留供回溯）
- **FR-EXT-LIGHT-05 基础实体库存入**：将`BasicEntityRecord`写入基础实体数据库，支持幂等写入（同一消息ID不重复插入）。

### 3.7.5 黑话学习模块

从情报数据中自动发现、学习新黑话，并生成可执行的正则表达式，供规则引擎实时过滤。

- **FR-SLANG-01 候选词发现**：在轻量通道处理时，AC自动机未匹配的词作为候选黑话。系统统计候选词的出现频次、上下文片段，存入候选词队列。候选词发现不消耗Token。

- **FR-SLANG-02 递进式学习状态机**：候选词状态流转如下：
  - `NEW`：出现1~5次，仅统计（统计预筛阶段，零Token）
  - `OBSERVED`：出现10次，触发第一次LLM推断
  - `LIKELY`：第二次推断确认疑似黑话（20次出现）
  - `CONFIRMED`：通过 60% 真实回测，确认写入词典
  - `REJECTED`：推断为非黑话 / 末位淘汰命中，进入静默期（30天内不再验证）；验证失败可重试最多3次
  - `STABLE`：出现500次后标记为稳定，不再推断
  - **退役机制（末位淘汰）**：CONFIRMED/STABLE 词若出现次数 ≥200 且命中率 <5%，由 `eliminate_weak_slangs()` 周期任务打入 REJECTED + 30天静默期，硬删 `slang_mappings` 避免死词长期占用 AC 自动机词典
  - **退役机制的存储层联动**（PG 是主存储，下游清理是 best-effort）：
    - **LightRAG 节点同步删除**：`GraphProcessor.delete_slang_entity(word)` 链式调 `adelete_by_entity` + `adelete_entity_relation`，避免已 REJECTED 词的释义污染下游 `mode='hybrid'` 检索
    - **seed_words 同步降级**：`demote_seed_word(words)` 把 `source='learned' AND status='active'` 的种子词标为 `degraded`，让 MediaCrawler 停止按这些死词拉取新语料；preset 来源不动
  - **沉默期防回流**：静默期内的 REJECTED 词在 `process_text` 入口被静默丢弃（不入 candidate、不增计数），防止 30 天后再次撞到 50 次触发"复活循环"

- **FR-SLANG-03 行为验证（三层闸门）**：**摒弃LLM自我置信度**，采用系统客观测试：
  - **第一层 LLM 自检**：LLM 需生成 `regex_pattern` + 2 个正例 + 2 个对抗性负例（负例**必须包含候选词核心字眼、但语境完全日常合法**，如"种草"→ 负例"我在阳台种草"）。系统自动测试：正例全命中、负例全不命中
  - **第二层 释义一致性**：从 `meaning` 提取核心词（2字以上），在 10 条 contexts_sample 中检查出现率，≥80% 视为一致
  - **第三层 真实回测（60% 阈值）**：取剩余约 40 条独立真实上下文（前序消息，未发给 LLM），用 `regex_pattern` 做命中率测试，**命中率 ≥ 60% 才算通过**。低于阈值直接计入重试，达 3 次后 REJECTED
  - **正例来源（独立样本原则）**：候选词X在消息M1中被发现，M1为触发源不用于验证；从同渠道历史消息中搜索其他包含X的消息（M2、M3...）作为独立正例
  - **重试机制**：验证失败后反馈给LLM重新生成regex_pattern，最多重试3次；3次都失败则REJECTED + 30 天静默期
  - **业务聚焦（2026-06-02 增）**：本系统重点是**字节跳动旗下产品的黑灰产业**（抖音 / TikTok / 头条 / 西瓜 / 飞书 / 豆包 / 剪映 等）。非字节系游戏账号交易（三角洲行动 / 和平精英 / 王者荣耀 等腾讯系产品）即使被 LLM 判为 slang，也必须 `is_valid_slang=false`
  - **硬黑名单规则（2026-06-02 增）**：以下类别**绝对不**是黑话，不论上下文：
    - 内容标签 / 话题标签：`原创` `笔记` `合集` `搞笑` `日常`
    - 通用商务平台词：`合作` `报价` `平台` `运营` `开通`
    - 用户画像：`大学生` `甜妹` `未成年`
    - 文本截断碎片：以"的"/"了" 开头/结尾的不完整句子
    - 平台官方词：`DOU+` `蒲公英` `闲鱼` `抖音`
    - 反诈宣传词：`反诈骗` `立案调查` `防诈骗`
  - **emoji / 符号保留（2026-06-02 增）**：候选词若含 emoji（💰😈🔞👩‍💻 等）或特殊符号（v/+/➗），`refined_word` 和 `regex_pattern` **必须完整保留**，不可替换为文字描述、不可删除。这些符号本身就是黑产规避审查的暗语组成（如 `加微💰` = 加微信谈价）。提取层使用 `emoji` Python 库（Unicode 16.0）做三路径候选捕获（jieba CJK + emoji-adjacent 滑动窗口 + `emoji.distinct_emoji_list` 兜底），AC Automaton byte-level Trie 天然支持 UTF-8 emoji（已通过 `tests/test_ac_automaton_emoji.py` 验证）

- **FR-SLANG-04 释义一致性验证**：同一候选词在多条消息中的LLM解析结果进行比对，`meaning`向量相似度>0.9则可信度上升，多次不一致则标记为"多义词"，继续观察，暂不收录。

- **FR-SLANG-05 词典同步**：CONFIRMED状态的黑话同步至：
  - AC自动机词典（热更新，下一条消息即可识别）
  - 正则规则库（regex_pattern写入，供实时过滤使用）

- **FR-SLANG-06 黑话主存（2026-06-03 重写）**：CONFIRMED 状态的黑话**主存位于 PostgreSQL `slang_mappings` 表**（已有 `slang_raw` / `meaning` / `regex_pattern` / `verified` / `source` / `confidence` 字段）。该表 + GIN 索引已提供完整的 hybrid 检索能力（按 `slang_raw` / `meaning` 模糊匹配）。
  - **LightRAG 不再承担 slang 节点存储**。旧实现对每个 CONFIRMED slang 调 `insert_custom_kg` 写一段 4 行 "黑话/释义/正则/来源" 自包含文本，但实际只产生孤立 slang 节点（无上下文关联、无共现边），且每淘汰一个词还需要 `adelete_by_entity` 双向同步。
  - 旧逻辑中"防止 REJECTED 词污染 hybrid 检索"的需求，100% 可由查询阶段 `JOIN slang_mappings WHERE status='CONFIRMED'` 替代，不需要图谱层。
  - 新逻辑：`pipeline/slang_learning.py:eliminate_weak_slangs` 末尾**不再调** `delete_slang_entity`；`services/daemon_scheduler.py:_persist_confirmed_slang` **不再调** `insert_custom_kg`。
  - 末位淘汰联动链路从 4 步（PG + seed + LightRAG + blacklist）降为 3 步。
  - 详见 `docs/MO图谱设计.md` §5.2。

- **FR-SLANG-07 Token成本控制**：
  - 统计预筛优先：先用词频筛选，LLM仅处理高置信候选
  - 批量验证：积累10-20个候选词后一次性LLM调用
  - 动态阈值：Token余量<30%时，提高触发阈值

- **FR-EVO-05 分类与过滤规则自动提案**：
  - **噪音规则进化**：自动进化Agent每日回溯被规则拦截的"噪声数据"，抽样1%交给LLM盲测。若LLM连续发现其中包含高价值实体，系统发出"规则误杀预警"，并由LLM提取引发误杀的异常模式（如某类正常文本特征），存入"噪声豁免白名单"。
  - **分类关键词进化**：当Embedding/LLM在第三层捕获了大量新样本，且这些样本具有高频共同特征词（如近期突增的"内部代下"），系统自动提取此类TF-IDF高权重的词汇，生成"分类规则补充提案"，自动追加到第一层（规则分类）的强特征词库中。

### 3.8 图谱构建通道：LightRAG图谱构建

适用于分流至图谱构建通道的高价值消息，利用LightRAG进行图谱化处理。

- **FR-EXT-DEEP-01 输入准备**：将消息的原始文本（保留emoji描述）以及前置分类标签、轻量抽取的初步实体结果，拼接为上下文增强文本。示例格式：“[前置分析：风险类型=账号交易, 已识别微信=dyhaomai] 原文：出抖号，千粉，加V:dyhaomai”。
- **FR-EXT-DEEP-02 调用LightRAG插入**：调用LightRAG的`ainsert`函数，传入增强后的文本。该函数内部自动执行：
  - LLM实体抽取与消歧
  - LLM关系抽取
  - 图谱节点和边的增量更新
- **FR-EXT-DEEP-03 Token消耗记录**：记录本次`ainsert`调用消耗的Token数量（通过API返回或估算），用于成本监控。
- **FR-EXT-DEEP-04 图谱更新反馈**：LightRAG处理完成后，系统应能够识别出新增/更新的实体和关系，并可选择性地将这些新发现的黑话、关联模式反馈至规则库（如发现新的黑话变种，自动加入词典待审核）。

### 3.9 图谱构建通道：VLM多模态处理（图片专项）

适用于分流至图谱构建通道且包含图片的高价值消息，利用VLM（视觉语言模型）进行图片语义理解和实体提取。

- **FR-EXT-VLM-01 图片语义描述生成**：调用本地部署的轻量VLM（如Qwen2-VL-2B）或云端VLM（如GPT-4o-mini），输入图片和上下文提示词（如"这是黑产情报图片，请提取其中的联系方式、账号、交易信息"），生成图片的语义描述文本。

- **FR-EXT-VLM-02 VLM结构化信息提取**：在生成语义描述的同时，要求VLM以结构化JSON格式输出提取的实体，包括：手机号、微信号、QQ号、邮箱、URL、平台账号、价格、交易对象等字段。

- **FR-EXT-VLM-03 多模态文本融合**：将VLM生成的语义描述拼接到原始消息文本后，格式如`[图片语义] xxx`。融合后的文本进入LightRAG `ainsert`流程，构建多模态知识图谱。

- **FR-EXT-VLM-04 多模态实体入库**：将VLM提取的结构化实体单独写入基础实体库，标记来源为`vlm`，并关联原图片的MD5标识，便于后续图片溯源和黑库扩充。

- **FR-EXT-VLM-05 Token消耗控制**：VLM调用是主要成本来源，需严格控制：
  - 仅对OCR未命中高价值实体且未命中黑库的图片调用VLM
  - 使用本地轻量VLM（Qwen2-VL-2B）优先于云端API
  - 设置单图Token上限（如max_tokens=500），避免单图过度解析
  - 记录每次VLM调用的Token消耗，用于成本监控和阈值动态调整

- **FR-EXT-VLM-06 新黑产图片上报与审核**：若VLM分析发现疑似新型黑产套路图片（如新型诈骗手法截图），自动上报至审核队列。审核Agent（独立于VLM处理流程）消费队列并执行二次确认，审核标准包括：
  - 新颖性：与黑库图片MD5相似度 < 0.8（非已知黑产）
  - 实体密度：包含手机号/微信号/URL ≥ 1个
  - 图片质量：分辨率 ≥ 640x480
  - 风险关联：涉及账号交易/洗钱/黑卡等目标风险类型
  
  审核通过 → 写入黑库 + 更新实体库；审核不通过 → 记录日志后丢弃。审核Agent作为第三者确保公平性，全部自动化不依赖人工。

### 3.10 查询响应与线索生成

当采集和处理任务完成（或达到预设超时）后，主控Agent基于构建好的基础实体库和知识图谱库，响应用户的初始查询。

- **FR-QRY-01 基础线索检索**：根据用户查询的时间范围、风险类型等参数，从基础实体库中检索匹配的`BasicEntityRecord`列表。
- **FR-QRY-02 图谱关联增强**：对于基础线索中出现的核心实体（如微信号、手机号、URL），向LightRAG发起关联查询，获取其直接关联的邻居实体和关系，补全“关系网络”信息。
- **FR-QRY-03 实体画像生成**：支持对单个实体生成情报画像，包含：基本信息、关联的所有其他实体（按关系分类）、历史活跃时间线、涉及的风险类型等。
- **FR-QRY-04 线索列表输出**：将检索到的线索以结构化列表形式展示给用户，每条线索至少展示：
  - 风险类型及标签
  - 关键实体摘要（如微信号、URL）
  - 关联实体数量（如“该微信关联3个账号、1个工具”）
  - 来源与时间
  - 分类依据（可选展开）
- **FR-QRY-05 线索详情展示**：支持用户点击/命令展开某条线索的完整详情，包括原始消息回溯、全部抽取实体、图谱关联视图（文本描述或可视化）。
- **FR-QRY-06 分析报告导出**：支持将当前查询的线索结果导出为结构化文件（JSON/CSV），或生成简短的文字报告摘要。

### 3.11 系统监控与自管理

- **FR-MON-01 Token消耗监控**：实时统计LLM API累计消耗Token量，接近限额时自动提高图谱构建通道的准入阈值。当Token余量 < 30%时，暂停图谱构建通道处理，优先保证轻量通道可用。
- **FR-MON-02 采集健康监控**：监控各渠道采集成功率、延迟，异常时发出告警（日志/界面提示）。
- **FR-MON-03 实体库状态**：展示基础实体库和图谱库的实体数量、关系数量、近期增长趋势。
- **FR-MON-04 日志记录**：全流程关键节点记录日志，包括消息处理量、分类分布、分流比例、错误信息等，便于调试和答辩复盘。

### 3.12 容错设计

#### 3.12.1 消息级容错

**消息处理状态机**：

| 状态 | 说明 | 后续状态 |
|------|------|----------|
| PENDING | 消息进入队列，待处理 | → PROCESSING |
| PROCESSING | 正在处理中 | → COMPLETED / FAILED |
| COMPLETED | 处理完成，已写入Entity和MessageRef | 终态 |
| FAILED | 处理失败（清洗失败/LLM超时等） | 直接丢弃，错误日志 |

**失败处理策略**：
- 失败消息直接丢弃（不重试，不进入死信队列）
- 错误日志记录：message_id、error_type、error_msg、timestamp、source_module
- 日志供事后分析和调优，不阻塞主流程

#### 3.12.2 组件级容错

**API接口降级策略**：
- 主API：DeepSeek
- 备用API1：Qwen（如主API失败/超时3秒）
- 备用API2：OpenAI兼容接口（如备用API1也失败）
- 所有API均失败时，记录错误日志，标记该消息为FAILED

**图片下载容错**：
- 下载失败时自动重试3次（间隔1秒、2秒、4秒）
- 仍失败则记录image_url、error_msg、timestamp到错误日志，跳过该图片不阻塞主流程

**查询超时机制**：
- 用户查询时启动采集任务，设置超时时间（默认30秒）
- 超时则返回已处理数据，后台继续处理未完成任务
- 下次查询时可获取完整结果

### 3.13 系统运行模式：双轨架构

系统采用"后台常态化巡逻（异步）"与"用户按需搜索（同步）+ 深度定向侦察（异步）"相分离的双轨架构。

#### 3.13.1 常态化巡逻模式（Background Pipeline）

- **机制**：系统后台24/7不间断运行。采集Agent根据种子词库和定时调度（如每15分钟一次），持续从各个渠道拉取数据，并流经清洗、分类、分流、提取全流水线，最终写入实体库和图谱。
- **目的**：建立庞大的历史情报资产库。用户在绝大多数情况下的查询，都是在这个已建好的库中进行。

#### 3.13.2 极速响应与深度侦察模式（Query & Active Recon）

当用户输入查询（如"近三天抖音账号买卖的线索"）时，系统执行两步走策略：

- **Step 1（毫秒级同步响应）**：主控Agent直接将查询转化为SQL/Cypher语句，检索本地已有的基础实体库和图谱库，并立即向前端返回现有结果（FR-QRY-01）。
- **Step 2（深度关联查询 - 异步执行）**：主控Agent生成一个任务ID（Task ID），对检索结果中的核心实体进行LightRAG关联扩展查询，获取关联实体和关系网络。前端轮询该Task ID，当关联分析完成后，推送完整结果到前端刷新列表。

## 4. 数据需求

### 4.1 数据模型概览

**存储架构：两库分离**
- 基础实体库（MySQL/MongoDB）：存储格式化实体和黑话映射
- LightRAG图谱库：存储产业/团伙之间的关联关系

**基础实体库表结构**：

| 表名 | 说明 | 核心字段 |
|------|------|----------|
| Entity | 实体主表 | entity_id, entity_type(WECHAT/PHONE/URL/QQ/SLANG...), raw_value, first_seen, last_seen, occurrence_count |
| MessageRef | 消息引用表 | ref_id, entity_id, message_id, source(regex/ocr/vlm/deep_channel), context_snippet, risk_label |
| SlangMapping | 黑话映射表 | mapping_id, slang_raw, meaning, regex_pattern, source(preset/learned), verified |

**LightRAG图谱库**：
- 节点：Entity.entity_id（实体引用，非重复存储）
- 边：产业间关系（使用、供应、关联等）
- 边属性：关系类型、置信度、来源证据

**系统目标**：情报分析——识别"哪些产业可能连接在一起"，不追踪个人。

### 4.2 实体唯一性键

| 实体类型 | 唯一性键 | 说明 |
|----------|----------|------|
| 微信号 | raw_value + source_channel | 同一人在不同渠道可能有不同微信号 |
| 手机号 | raw_value | 全国唯一 |
| QQ号 | raw_value | 全国唯一 |
| URL | domain + path | 短链需归一化 |
| 黑话 | slang_normalized | 同一词在不同渠道含义可能不同，需按渠道分别管理 |

### 4.3 多通道写入流程

所有消息的格式化实体都写入基础实体库，只有深度通道的消息才会写入LightRAG图谱发现产业关联。

```
消息 → 清洗 → 分类 → 分流
                  ↓
        ┌─────────┴─────────┐
        ↓                   ↓
  轻量通道(90%+)     深度通道(<10%)
        ↓                   ↓
  实体抽取           实体抽取 + 关系发现
        ↓                   ↓
  写入Entity         写入Entity
  + MessageRef       + MessageRef
                      + LightRAG关系边
```

**失败处理**：消息处理失败时直接丢弃，错误日志记录（message_id、error_type、error_msg、timestamp），不重试。

### 4.4 实体与关系定义（图谱Schema）

需预定义以下实体类型（Node Labels）和关系类型（Edge Labels），具体已在架构设计中定义，此处从略，但系统需内置此Schema以供LightRAG进行实体链接和关系推断。

## 5. 外部接口需求

### 5.1 情报源接口
- **Telegram API (MTProto/TDLib)**：支持获取群组消息、历史消息。
- **HTTP/HTTPS爬虫**：支持对论坛、贴吧等网页的定向抓取。

### 5.2 LLM API
- 提供OpenAI兼容接口，支持传入System Prompt和User Message，返回结构化JSON。
- 系统需配置API密钥、端点URL、模型名称。

### 5.3 LightRAG库接口
- `ainsert(text, ...)`：异步插入文本，自动更新图谱。
- `aquery(query_text, mode="local"/"global")`：支持图谱查询和检索。
- 原生图存储访问接口（可选，用于自定义图谱遍历）。

## 6. 非功能需求

### 6.1 性能需求
- **采集延迟**：对于TG群组，新消息到达后5分钟内完成采集。
- **处理吞吐**：支持每分钟处理不少于100条消息（轻量通道）。
- **查询响应**：常规查询（如“近三天某风险类型线索”）需在30秒内返回初步结果。

### 6.2 成本控制需求
- **Token用量**：单条消息的平均LLM Token消耗需控制在<500 token（计入图谱构建通道分摊）。
- **本地模型优先**：分类和向量化优先使用本地部署的轻量模型，不得频繁调用LLM做简单任务。

### 6.3 可扩展性需求
- 支持热加载黑话词典和正则规则，无需重启服务。
- 支持新增情报源渠道，只需实现统一采集适配器接口。
- 支持新增风险类别和实体类型，只需更新配置和少量标注。

### 6.4 可维护性与可观测性
- 提供清晰的结构化日志，区分INFO/WARN/ERROR级别。
- 关键处理环节的计数和耗时统计（采集量、清洗通过量、分类分布、轻量/图谱构建通道分流比、LLM调用次数及Token消耗）。

## 7. 典型运行场景示例

**场景：用户查询”近三天抖音账号买卖线索”**

1. 用户通过交互界面输入自然语言查询。
2. 主控Agent解析查询，确定时间范围、风险类型`账号交易`、目标平台`抖音`。
3. 主控Agent从本地基础实体库和LightRAG图谱库检索已采集的数据，直接返回初步结果（毫秒级响应）。
4. 主控Agent对检索结果中的核心实体（如微信号）发起LightRAG关联扩展查询，获取关联实体和关系网络。
5. 系统筛选出标记为`账号交易`的线索，生成5条高价值线索。
6. 主控Agent将线索列表返回给用户，包含每条线索的摘要。
7. 用户点击某条线索，查看详情：完整实体列表、图谱关联（如该微信号关联的其他账号、工具）、原始消息回溯。
8. 用户对线索质量和分类合理性给予肯定，答辩演示成功。
