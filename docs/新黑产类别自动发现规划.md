### 整体工作流

```
                        ┌────────────────────────────────────────┐
                        │  每日调度 (unknown_discovery.run)       │
                        └──────────────────┬─────────────────────┘
                                           ↓
              ┌─────────────────────────────────────────────────┐
              │  1. 信号检测: 拉取近 7 天 risk_label_level1 =   │
              │     '未知/其他' 的样本, 按 cleaned_text 去重     │
              └──────────────────────────┬──────────────────────┘
                                         ↓
              ┌─────────────────────────────────────────────────┐
              │  2. Embedding: Ollama bge-m3 → 1024-dim 向量    │
              │     (单次 batch 调用, bge-m3 1024 维天然适配)    │
              └──────────────────────────┬──────────────────────┘
                                         ↓
              ┌─────────────────────────────────────────────────┐
              │  3. UMAP 降维: 1024D → 10D                      │
              │     • n_neighbors=15 (大规模数据时调 30)        │
              │     • min_dist=0.0, metric='cosine'             │
              │     • 模型持久化到 umap_unknown_discovery.pkl    │
              │       支持 transform() 增量推理                 │
              └──────────────────────────┬──────────────────────┘
                                         ↓
              ┌─────────────────────────────────────────────────┐
              │  4. HDBSCAN 聚类: min_cluster_size=30           │
              │     • 在 10D 空间做密度聚类                      │
              │     • 噪声点 (label=-1) 不进入提议流程          │
              └──────────────────────────┬──────────────────────┘
                                         ↓
              ┌─────────────────────────────────────────────────┐
              │  5. 准入门槛 + 中心采样                          │
              │     • cluster_size >= 50 才进入提议             │
              │     • 跨 3 天出现 (待 daemon 跑 1-2 周后启用)   │
              │     • 簇内到质心最近的 Top 30 样本注入 LLM       │
              └──────────────────────────┬──────────────────────┘
                                         ↓
              ┌─────────────────────────────────────────────────┐
              │  6. 强约束 LLM 命名 (pipeline/prompts.py)       │
              │     System-Task-Rules-Output 4 段结构:           │
              │       • System: 资深风控专家人设                 │
              │       • Task: 动态注入 taxonomy + 簇样本        │
              │       • Rules: 4 条硬规则                        │
              │         - 优先归类 (不轻易生造)                  │
              │         - 高度抽象 (禁品牌名/App名/具体金额)     │
              │         - 2-6 汉字命名                          │
              │         - 无意义判 IRRELEVANT/普通内容          │
              │       • Output: JSON (chain_of_thought /         │
              │         is_new_category / level1 / level2 /     │
              │         confidence)                             │
              └──────────────────────────┬──────────────────────┘
                                         ↓
              ┌─────────────────────────────────────────────────┐
              │  7. 代码级三道断言 (防 LLM 脱缰)                 │
              │     ① 长度: proposed_level2 ∈ [2, 6] 汉字       │
              │     ② 置信度: confidence >= 0.8                  │
              │     ③ 类别: is_new_category=true (否则归"未知") │
              │     任何一道不通过 → 丢弃                       │
              └──────────────────────────┬──────────────────────┘
                                         ↓
              ┌─────────────────────────────────────────────────┐
              │  8. 候选池去重 (防"跑分洗钱"vs"代收代付"重复)   │
              │     • 与 existing taxonomy 余弦相似 > 0.85 →    │
              │       强制归并到现有 level1                       │
              │     • 与 pending_category_proposals 池查重       │
              │       (NumPy 初期 / pgvector 后期)              │
              └──────────────────────────┬──────────────────────┘
                                         ↓
              ┌─────────────────────────────────────────────────┐
              │  9. 写入 antiblack.pending_category_proposals   │
              │     (含 embedding 列, sample_texts JSONB)        │
              └──────────────────────────┬──────────────────────┘
                                         ↓
              人工审核 (status: pending → approved/rejected/merged)
```

### 关键参数（`config.yaml`）

```yaml
unknown_discovery:
  schedule_interval_hours: 24
  min_cluster_size: 30
  umap_n_components: 10
  umap_n_neighbors: 15       # 大规模调 30, 详见调优备忘录
  min_cluster_size_for_proposal: 50
  top_k_samples_per_cluster: 30
  cosine_dedup_threshold: 0.85
  min_level2_chars: 2
  max_level2_chars: 6
  min_llm_confidence: 0.8
```

### 数据库表 (`migrations/phase2_init.sql`)

| 表名 | 用途 | 关键列 |
|---|---|---|
| `antiblack.pending_category_proposals` | 待审核池 | `proposal_id`, `cluster_id`, `proposed_level1/level2`, `chain_of_thought`, `llm_confidence`, `sample_texts` (JSONB), `sample_size`, `embedding` (DOUBLE PRECISION[]), `status` |
| `antiblack.slang_evaluations` | slang→rule 桥接的去重缓存 | `slang_candidate_id`, `eval_status` |
| `antiblack.dynamic_rules` | slang→rule 桥接产出的规则 | `rule_id`, `level1_label`, `level2_label`, `keywords` (JSONB), `hit_count`, `correct_count`, `is_enabled` |

### 调优备忘录

| 参数 | 当前值 | 何时调整 |
|---|---|---|
| UMAP `n_neighbors` | 15 | 每日新增 > 5000 条时调到 30, 让大簇结构更稳固 |
| UMAP `n_components` | 10 | **绝对不要降到 2-3 维**（那是画散点图给人看的, 会挤压不相关类别） |
| HDBSCAN `min_cluster_size` | 30 | 样本量充足后调 50, 减少噪声簇 |
| `cosine_dedup_threshold` | 0.85 | 候选池超过 10000 时, 切到 pgvector 加速 |

### 性能优化路径

| 阶段 | 候选池规模 | 实现 | 复杂度 |
|---|---|---|---|
| 初期 | < 1000 | NumPy 矩阵乘法 | $O(N)$ |
| 中期 | 1000-10000 | 预计算候选 embedding 矩阵 + batch dot product | $O(N \cdot d)$ |
| 后期 | > 10000 | **PostgreSQL pgvector** + IVF 索引 | 亚毫秒级 |

**pgvector 切换条件**：
- 候选池行数 > 10000
- 单次判重 P95 > 50ms
- 已部署 pgvector 扩展

<summary>📜 V1 规划（简单 HDBSCAN on 1024D，未实现）</summary>

> **V1 草案 (2026-05-27)**：对 1024 维 embedding 直接做 HDBSCAN 聚类。
>
> V1 存在两个核心问题，已被 V2 解决：
> 1. **维数灾难**：1024 维直接做密度聚类，所有样本都会被判为噪声或挤成一团（任意两点距离趋于一致）。
>    - V2 解决：UMAP 先降到 10D（保留局部+全局拓扑, 支持 transform 增量）
> 2. **LLM 发散**：直接问"这是什么类别"，LLM 容易起具体名（如"微信朋友圈卖高仿劳力士手表"）
>    - V2 解决：System-Task-Rules-Output 4 段强约束 Prompt + 代码级三道断言（查重/长度/置信度）
>
> V1 完整草案保留在下方，供参考。
>
> ---
>
> ## 1. 背景与问题
>
> ### 1.1 现状
> 当前分类体系是**静态预置**的，4 个一级分类、若干二级分类硬编码在 `pipeline/classifier.py` 中。
> **问题**：黑产手法不断进化，出现新类型（如"内部代下"、"薅羊毛"、"跑分洗钱"）时，系统无法自动发现和适应。
>
> ### 1.2 目标
> 当新型黑产套路出现时，系统能够自动发现 + LLM 验证 + 自动入库。
>
> ---
>
> ## 2. 设计方案
>
> ### 2.1 整体工作流
> ```
> ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
> │  信号检测   │───→│  聚类分析    │───→│  LLM 验证    │
> │  (Signals) │    │  (Clustering)│    │  (LLM Judge) │
> └──────────────┘    └──────────────┘    └──────────────┘
>        │                                        │
>        │              ┌──────────────┐          │
>        └─────────────→│  自动入库   │←─────────┘
>                       │  (Auto-enroll)│
>                       └──────────────┘
> ```
>
> ### 2.2 Step 1：信号检测
> | 信号 | 阈值 | 说明 |
> |------|------|------|
> | 低置信文本累积 | 置信度 < 0.6 的文本超过 N 条 | 现有分类器不确定 |
> | 新型 slang 爆发 | slang_candidates 出现 > 20 次/天的新词 | 词汇量突增 |
> | 聚类离群点 | embedding 空间中出现新的紧密聚类 | 结构变化 |
>
> ### 2.3 Step 2：聚类分析
> ```python
> from sklearn.cluster import HDBSCAN
> def detect_anomaly_clusters(texts: List[str], min_cluster_size: int = 10):
>     embeddings = embedding_model.encode(texts)
>     clusterer = HDBSCAN(min_cluster_size=min_cluster_size, min_samples=5)
>     labels = clusterer.fit_predict(embeddings)
>     # V2 NOTE: 在 1024D 直接 HDBSCAN 会遭遇维数灾难, 需先 UMAP 降维
>     anomaly_mask = labels == -1
>     ...
> ```
>
> ### 2.4 Step 3：LLM 验证 (V1 简版 Prompt)
> ```
> 你是一个黑产情报分类专家。以下是从情报数据中发现的异常文本簇：
> 文本样例：{cluster_samples}
> 请判断：1) 是否独立新黑产类别; 2) 类别名; 3) 5-10 个特征词; 4) 理由
> ```
> V2 替换为 `pipeline/prompts.py::build_cluster_naming_prompt()` 完整 4 段强约束 Prompt
>
> ### 2.5 Step 4：自动入库 (V1 简版)
> - 入录条件：`is_new_category=true` 且 `confidence >= 0.8`
> - V2 替换为: 代码级三道断言（查重/长度/置信度）+ 候选池去重 + 人工审核
>
> ### 2.6 回退机制
> V1 7 天观察期 → V2 直接由代码级断言 + 候选池去重 + 人工审核取代

## 与黑话学习的关系

V2 进一步强化了两者的协同：

```
unknown_discovery  ──────→  pending_category_proposals  ──[人工审核]──→  taxonomy 更新
        │                                                                ↓
        │                                                  slang_to_rule_bridge
        │                                                                ↓
        │                                                  dynamic_rules (新关键词进 Stage 1)
        │                                                                ↓
        └────────────[反馈信号: 高频新 slang 触发]──────────────────→  slang_candidates
```

**区别（V2 更新）**：

| | 类别发现 | 黑话学习 |
|---|---|---|
| **粒度** | 新风险类别（一级/二级） | 单个黑话词 |
| **输入** | UMAP+HDBSCAN 聚类 + LLM 强约束命名 | 词频统计 + LLM 验证 |
| **输出** | `pending_category_proposals` | `slang_mappings` + 桥接后入 `dynamic_rules` |
| **自动化** | 半自动（代码级断言 + 人工审核） | 半自动（CONFIRMED 才入库） |
| **验证机制** | 三道代码级断言 + 候选池去重 | LLM 自检 + 释义一致性 + 60% 真实回测 |
| **生命周期** | 人工审核 (status: pending/approved/rejected/merged) | 30 天静默期后重新观察（避免死循环） |
| **退役** | 人工 reject | 出现 ≥200 且命中率 <5% → 末位淘汰 → REJECTED + 静默 |
